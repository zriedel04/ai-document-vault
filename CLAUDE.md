# Claude Code specifics

The shared project rules, workflow, review process and commands are in `AGENTS.md`, imported above. This file adds only what is specific to Claude Code.

## Responding to review

Codex may review any PR and post comments. Retrieve every finding and sort each into one of four categories before touching code:

| Category | What to do |
| --- | --- |
| Valid, fix now | Make the smallest appropriate fix, add or update tests, run the relevant checks, push, reply on the thread with the commit and what changed, and resolve it |
| Valid, but the proposed fix should change | Fix the underlying problem a better way and say in the reply why the suggestion was not applied as written |
| Valid, but outside this PR's scope | Do not widen the PR. Reply with why, and recommend a follow-up issue (open it only if the owner agrees) |
| Not valid | Reply with the evidence, such as the `file:line` or a test that shows it, and resolve the thread |

- Never apply a suggestion blindly, and never dismiss one without checking it.
- Address one Codex pass at a time. Do not request another review and do not loop: after fixing a pass, report to the owner, who decides whether another review is needed.
- Do not merge a pull request, whatever its review or CI state. The owner merges after explicitly approving.
- Treat repeated findings as a signal about the author, not just the code. Record the pattern under "Lessons from review" below so the next change avoids it.

## Lessons from review

These patterns came up repeatedly in Codex's reviews of the repository safety check (`scripts/check_repo_safety.py`, six review rounds, about fifteen findings) and of the ADR checker. Check for them before pushing, not after a review.

1. **Fix the class, not the instance.** A finding names one example (`.epub`, `.ppk`, a zip). Before replying, list the whole class (every ebook format, every key format, every archive format) and cover all of it, with a test that fails when a member is missing. Fixing only the named example invited the next round. The same holds for a permission: the blob seal tested one write bit (the owner's), so a mode such as `0o446` stayed writable by anyone; compare the whole mode with the exact value you want (`0o444`) instead of testing the bit a finding names. The blob store showed it twice: uniqueness was enforced on the file name (`<hash>.txt`) instead of on the hash it stands for, so the same bytes imported as `.txt` and `.md` made two blobs, and a guarantee about the end state (every blob is read-only) held only if the process was not killed in between. Enforce a rule on the key, not on a name derived from it (and treat two names for one key as damage that a lookup reports, a scan does not trust and a delete removes completely, instead of letting `find` pick the first), and for every step that has a crash window ask what the next start-up does about it (`seal()`, `clean_temp()`).
2. **Close every layer of a rule.** A protection usually exists in several places that must agree: `.gitignore`, the path rule in the checker, the content rule (file signature), the staged index, the working tree and git history. Adding a suffix without its signature check, or an ignore rule without a checker rule (`vault/`, `*.bak`), left a gap. When adding to one layer, list the others and cover them or say why not. The start-up access check listed the vault's files by name and missed SQLite's rollback journal, which the safety check and `.gitignore` already knew as private database data: when a rule names a file kind in one place, search the repository for the same kind elsewhere, and check a folder by listing it rather than by a list of names. The next round found the same gap one level down: the check covered the folder and its direct entries but not the files below the subfolders, and Windows lets any account open a file by its path when its own list names it, so a rule about access to files must cover the whole tree, not a fixed depth.
3. **Assume the bypass.** Safety guards must survive `git add -f`, a renamed or deleted file, a file edited after staging, a file with the wrong extension, and a blob that only exists in history. Test each of these as a scenario, not just the happy path. For code that touches the file system, the bypass is a link: `is_file()`, `stat()`, `chmod()` and `mkdir(exist_ok=True)` all follow symbolic links, so a link in the place of a blob or one of its folders made the blob store find, chmod or publish into something outside the vault. Use `lstat`, refuse links and Windows reparse points (junctions have the reparse attribute, not the symlink mode) at every level before using a path, report them in the integrity scan, and test a link to an outside file, a link at each folder level and a dangling link. Also test the failure path of an operation that first loosens something (a delete that made a blob writable and then failed left it writable). Links are a class with more members than symlinks and junctions: a hard link is a regular file with the same inode (check the link count before `chmod`), and every folder the code works in (the temporary folder, not only the hash folders) needs the same check. A recovery method that nothing calls is not a recovery: wire it into start-up and test the start-up.
4. **Read the whole input.** Fixed-size reads (16 bytes) missed signatures that sit deeper in the file (tar at offset 257). State the assumption about input size or position and test the boundary. The same goes for the end of a string: in Python `$` also matches before a trailing newline, so `re.match(r"^...$", "name\n")` succeeds. Check a whole value with `fullmatch` and test every pattern with a trailing `\n`, `\r` and space. Two more forms from the file validator: a check that runs after a library has built its objects is too late (`zipfile` reads the whole central directory before any entry count can be checked, so bound the claim from the end record first and prove with a test that the library is never opened), and a marker says how to read the content, not that the content is valid (a byte order mark made any bytes after it text; decode them and judge the result). Two more from the second pass: when you copy a library's parsing to judge a claim first, copy its whole rule, not the common layout (`zipfile` follows the ZIP64 locator to a record that may sit before an extensible data sector, so a fixed-offset read judged a different record than the library would use; build the unusual layout as a file, prove with a control that the library opens it, remembering that this differs between patch releases of Python and CI runs two of them, and mutate the code back to see the test fail), and the end of the input is a different case from a cut input (a head cut mid-character is fine, a whole file that ends mid-character is not, so pass that fact to the decoder). The third pass showed the other half: the project supports every 3.12 patch release, and `zipfile` differs between them, so a preflight that mirrors one release judges a different record than another release reads. When code must agree with a library, bound every place any supported version may read (and test that the value the installed version reads is among those judged, on each Python in CI), or raise the minimum version. The same test found a field-index slip (`fields[8]` is the directory size, not the entry count) that earlier fixtures hid because their numbers were all huge: write a fixture with distinct small values for each field.
5. **Review your own diff adversarially before pushing.** Ask what a careless or hostile user would commit that this change still lets through, and what legitimate file it would wrongly block (the planned `backend/src/vault/` package is source code, not a vault folder). Compare every new dependency and framework with the stack table in `docs/architecture.md`: the frontend shell shipped React Router where the approved plan says TanStack Router, which needed either a switch or an ADR.
6. **Do not state a claim you have not checked.** One reply said every archive suffix had a signature check when `.tar` and `.iso` did not. Verify a claim against the code before posting it.
7. **Validate what a value points at, not just its shape.** A status naming a superseding ADR, a link to spike results and a file name pattern each passed a loose check (a regex, `is_file()`, a glob) while accepting nonsense (`ADR 9999`, `docs/architecture.md`, `0016_typo.md`). For every reference or naming rule, test a missing target, a wrong kind of target, and a name that nearly matches, and make the checker report what it skips instead of ignoring it. Check the target's state and contents too (a replacement ADR must be Accepted and point back; a spike file must have its sections filled in), and check both directions of a link. Even so, a structural check cannot prove a fact such as "the experiment was run on the Windows PC": say so in the docs and leave that to the owner's review.
8. **Allow by construction, not by appearance.** A privacy guarantee that rests on a value "looking harmless" fails on the first harmless-looking leak: the logging check let a one-word piece of document text through because it matched the identifier pattern, and it copied field names into the log unchecked. Make the default deny (a type or an explicit marker says a value is safe), cover every channel into the output (values, field names, event names, logger names, exception messages, third-party libraries, whose loggers such as uvicorn's access log write request URLs, and the formatter's own failure path, because Python prints the raw message when a handler raises), and test with realistic document text, not only obviously bad input. A type is not provenance: after redacting `str` the next round found that a plain `int` or `float` parsed from a document leaked too, so a value needs an explicit marker (`metric()`, `identifier()`) that says the application produced it. When a parser skips a clause it does not understand (an SPDX `WITH` exception), it must fail closed. When two checks read the same data, make them read the same source through one function: the licence gate decided by the SPDX expression while the reviewed-exception check looked at any field, so an old MPL classifier rescued a GPL expression. The same rule applies to access control: the Windows folder check listed broad groups to reject (Everyone, Users) and so let a second named account or a domain group through; it now accepts only the current user and a few system principals. A credential's transport has a scope too: the install token in a `SameSite=Strict` cookie reached every port on `localhost`, because cookies are scoped by host and not by port; it is now sent only as an `Authorization` header from the page's own origin storage. When a secret leaves the process, ask who else receives it, not only who may send it.
9. **Check what your tooling enforces before claiming it.** The logging docstring said mypy rejects a computed event name (it does not enforce `LiteralString`) and that libraries "never see document content" (uvicorn logs every request URL). Run the claim as an experiment (a short file that should fail, a request through a real server) before writing it down, and make a regression test fail when you remove the fix. The same goes for a race fix: the blob store claim passed the Windows job once and failed on the next run, because Windows reports a name that is being deleted as `PermissionError`, not `FileExistsError`. One green run proves nothing about a race, so loop the race test many times, and say in the reply what was run on which system.
10. **Check that interchangeable evidence is complete.** An eval `alternative` counts as a full answer, so a passage that gives only part of it (a date without the time, one of three reasons) inflates retrieval scores. The first review found one, and the audit found three more. For every alternative, compare it with the whole expected answer; `test_corpus.py` checks that the sources and each alternative carry every number of the expected answer and that no one document holds all the quotes of a `multi_doc` question, and the facts in words are yours to check. The second review round found the same gap again in the sources (three requirements missing from a list) and a `multi_doc` question one document could answer. The fourth round found the other direction: a `multi_doc` source that was not needed because another cited document repeated its fact (the email restated the syllabus rule, and the journal and the email both dated the breakage), and a version question whose baseline was only a distractor. For every `multi_doc` question, remove each source in turn and ask whether the rest still answer it; a mechanical number check was tried and only flagged incidental matches, so this stays a review step. The fifth round found the opposite gap: a document that also answers the question was not accepted (the edited standup kept the SQLite line; the project journal restated the chat decision), so a correct retrieval would score as a miss. `test_corpus.py` now fails if any other document holds a source quote verbatim; a paraphrase in another document is again a review step. For every answerable question, ask which other documents give the whole answer, and leave out one that gives only part of it (the journal has the laptop repair but not that Sam held the draft). The sixth round found the group form of the same gap: two syllabi that each give one final date answered the "which final comes first" question together, and the eval format only has single-passage alternatives, so that question was replaced. If a fact is spread over documents in a way an alternative cannot express, change the question and do not ship the gap. The seventh round found the sources side again, in two forms: an answer that names a shop the sources do not mention, and an answer that says what is absent ("not yet graded") while citing only one row of the table, which cannot show an absence. `test_corpus.py` now checks that every name in an answer is in a source quote and that the absence question cites the whole table. For a claim that something is missing, cite the complete list. The eighth round found the same two gaps in other questions: a passage taken out of its context cannot support the answer (a CSV row without its header row does not say whose hours `41` are, and a total does not show what it adds up), a comparison between two versions needs both ends of both lists (the last item and the next heading) to show that nothing else was added, and a history question left out a stage of the decision (the requirement that put chat in for a while) because that document was listed as a distractor. For every cited passage, ask whether it still proves the claim when read alone, and for every distractor, ask whether it is a stage of the story. `test_corpus.py` now requires CSV sources to be the whole table, the version comparison to cite the list ends, and the chat question to cite the first requirements draft. The ninth round found the absence question again: it now cited the whole grades table but only two items of the syllabus list that names every component, so the list that shows what the course has in all was still not whole. The class is "a claim about what is missing needs the whole of both sides", so the question now cites the complete grading list too, and `test_corpus.py` compares it with the syllabus text.

Add to this list when a new pattern appears in review, and remove entries that no longer apply.

## Keeping documents current

- Update `AGENTS.md`, this file, ADRs, tests and architecture docs in the same PR as the change they describe.
- A rule that applies to every AI tool belongs in `AGENTS.md`. Put it here only if it is meaningful to Claude Code alone.
