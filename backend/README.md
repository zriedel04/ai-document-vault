# Backend

The FastAPI process that will own the HTTP API, the background worker, the database and the vault folder (see `docs/architecture.md`). It has an app factory, request protections, the vault folder rules, the database with its migrations, settings and logging. Document handling comes later.

## Commands

Run from this folder. Python 3.12 and [uv](https://docs.astral.sh/uv/) are required.

| Task | Command |
| --- | --- |
| Install | `uv sync` |
| Run the server | `uv run python -m vault` |
| Check the vault, read-only (`vault.ps1 check`) | `uv run python -m vault.check` |
| Tests with coverage | `uv run pytest` |
| Lint and format check | `uv run ruff check . && uv run ruff format --check .` |
| Type check | `uv run mypy` |
| Licence check | `uv run python ../scripts/check_python_licenses.py --ignore vault` |
| Export the API schema for the frontend | `uv run python -m vault.openapi ../frontend/openapi.json` |
| Back up the vault (what `.\vault.ps1 backup -To` runs) | `uv run python -m vault.backup --to <folder>` |

## Settings

`config.toml` (copy `../config.example.toml`) is read from the current folder, or from the path in `AIVAULT_CONFIG`. Environment variables override it: `AIVAULT_SERVER__PORT=9000`. Unknown keys are an error. The server only accepts `127.0.0.1`, `localhost` or `::1` as `server.host`, the three spellings the Host check accepts. If `frontend/dist/index.html` exists (or `frontend.dist` points at a build), the server also serves the built frontend, so the app and the API share one origin; other GETs without a file extension return `index.html` for client-side routes, and unknown `/api/...` paths are 404.

## Security

Every request passes through `vault.core.security.LocalSecurityMiddleware`, which is deny by default. The server binds to loopback only, but that does not stop other websites or other accounts on the same PC, so:

- `Host` must be `localhost`, `127.0.0.1` or `[::1]`, with an optional port (this stops DNS rebinding).
- Any method except GET, HEAD and OPTIONS needs an `Origin` equal to `http://` plus the `Host` value.
- Every `/api` path except `GET /api/health` needs the install's token as `Authorization: Bearer <token>`, and only that: there is no cookie and no sign-in call. A browser sends a cookie to every port on the same host name, so another local program (a dev server on `localhost:3000`, say) would receive it; a token that the page keeps in its own origin's storage and sends in a header reaches nobody else. `GET /api/session` returns the signed-in user, which is how the page learns whether its token works. The token reaches the page through the launcher, which opens the app at `http://127.0.0.1:8765/#token=<token>`: a URL fragment is never sent to a server, the page copies it into `sessionStorage` (per origin and tab) and removes it from the address bar. The launcher (PR 6) and the frontend client change do that after this PR; until then only a client that holds the token can use the API.
- `GET /api/health` also answers with `launch`, the value of the `VAULT_LAUNCH_ID` environment variable when it has the token's shape (otherwise `null`). The launcher starts the server with a fresh random value there and opens the browser with the token only when the server answers with it, so a program that took the port while the server was starting never receives the token (`docs/launcher.md`). The value is no secret once the server is up.
- There is no CORS configuration: no other origin is ever allowed. A refusal is a 403 (Host or Origin) or 401 (token) with a fixed body, and the log line carries the reason only, never a header value.
- Every response, refusals and the error page included, carries the headers in `vault.core.headers`: a `Content-Security-Policy` that allows scripts only as files from this origin (no inline script, no `eval`) and lets requests, images and fonts go only to this origin, plus `nosniff`, `no-referrer`, no framing and same-origin opener and resource policies. Styles may be inline because Mantine writes its theme into `<style>` elements at run time; with every outward channel closed, an injected style cannot carry data away. This is the second line behind React's text rendering for the token in `sessionStorage` (ADR 0016). FastAPI's `/api/docs` page needs a CDN and an inline script, which the policy blocks; it was never reachable from a browser, which cannot send the token header, so read `/api/openapi.json` instead.

The page gets the token from the launcher in the address fragment (`/#token=...`, never sent to the server) or by paste, keeps it in `sessionStorage` and sends it as the header; the server never serves it (ADR 0016, `frontend/src/api/token.ts`). The token is the file `local-token` in the vault folder, created on first start with mode 0600. On Windows `chmod` does nothing useful and a folder under a drive root lets every account on the PC read it, so `vault.storage.acl` makes the vault folder owner-only (it removes the inherited entries and grants only the current user, through PowerShell), reads the access list back and refuses to start unless every entry that grants access names your account, SYSTEM or the Administrators group (an administrator can take ownership of any folder anyway). A second account or a domain group named in the list, as well as Users, Authenticated Users or Everyone, makes the folder not private. The folder's owner has to be your account, SYSTEM or Administrators too, because an owner can rewrite the list. An existing vault is also checked entry by entry at start-up: the token, both databases with their SQLite side files (`-wal`, `-shm` and the rollback journal `-journal`, any of which can hold database pages) and the four subfolders by name, plus whatever else sits directly in the vault folder under any other name (a super-journal, a copied backup, a stray file). A file moved in from another folder keeps its own access list, so one that is open stops the start and is named in the error, without being changed. Then every file and folder below the vault folder is checked the same way (links are listed but not followed), because Windows lets any account open a file whose path it knows when that file's own access list names it, even if the folders above are private, and a tree moved in keeps its files' lists. PowerShell reads one access list per file and reports only the distinct lists with a count and a few example paths relative to the vault folder, so the output stays small; the walk is allowed 15 minutes, and a vault with tens of thousands of files will take a noticeable time to start (not yet measured; if it is slow on the real vault, a follow-up can remember what was verified). Restoring by copying is still the easy way to get files that take the folder's list. A folder that already has files and is not private is not changed; the error says how to fix it. A file that is not a well-formed token stops the start-up: delete it to get a new one. Without a vault folder (demo mode, tests) the token is random for that process and nobody holds it, so only the open endpoints work. Every endpoint takes the user from `Depends(current_user)`, which today returns the one local user; real login would change that function only.

## Vault folder and database

`vault.path` must be an absolute folder outside every Git repository: a path whose resolved location has a `.git` file or folder (or is a bare repository) at or above it is refused before anything is created, so `..` and symbolic links cannot get around it. `ensure_vault` then creates `blobs/`, `derived/`, `logs/` and `backups/`. The start-up also migrates `vault.db` with Alembic (`vault.db.migrate.upgrade_to_latest`) and opens it through `vault.db.engine.create_vault_engine`: WAL mode (an error if the file system cannot do it), `synchronous=NORMAL`, foreign keys on and a busy timeout, on every connection. Table definitions are in `vault/db/schema.py` and each change to them needs a revision in `vault/db/migrations/versions/`; a test fails if the two disagree. `env.py` does not call `fileConfig`, because that would replace the safe logging.

The document tables (`blobs`, `documents`, `document_versions`, `import_sources`, revision `0002`) follow `docs/architecture.md` section 6: importing the same bytes again adds an `import_sources` row, not a document, and two documents may share a blob. Row ids are ULIDs made by `vault.db.ids` (time-ordered, saying nothing about the document). The database checks the shape of what it stores as well (CHECK constraints for ids, hashes, extensions, media types, states, origins, methods and the JSON folder list), so a bug or a hand edit cannot store a value the application would not write. A document's current version must be one of its own versions (a foreign key on the pair of ids), and a document in the trash has the state `trashed`, the time it went there and the state to restore (`state_before_trash`), all three or none (ADR 0005); a test compares those constraints with `schema.py`, because Alembic's own comparison skips them. Deleting a document deletes its versions and sources; a blob that a version uses, and a version that is current, cannot be deleted. `import_sources` holds the owner's own file and folder names, so it is never logged. The importer (below) writes them.

## Importing a file

`vault.ingest.importer.Importer.import_file` is Tier A of the pipeline (`docs/architecture.md` section 7). It validates the file where it is, copies it into the blob store, and validates the stored copy again. The source can change between the first check and the copy, the blob cannot, so the second check is the one that counts, and a blob the import created for bytes that fail it is removed. Then, in one transaction, it writes the blob row and either a new document (state `processing`) with its first version, its import source and an `extract` job, or, when a document already holds these bytes, only a new import source for it. The same file imported twice is one document with two sources and one job. A document in the trash that is imported again leaves the trash with the state it had before. The transaction's first statement is a write, which takes SQLite's write lock, so two imports of the same bytes at once give one document (a test runs eight threads, each with its own connection). A permanent delete of a document with the same bytes can remove the blob's file after the copy found it: the transaction checks, under the write lock, that the file is still there and the import copies the source again if it is not (`vault.storage.purge`). A refusal of the stored copy counts only if the file that was checked is still the blob afterwards, compared by identity (device, file number and status-change time, `BlobStore.identity`) and not by name, because a delete and another import can remove and store the same bytes again under the same name while it is checked; otherwise the import tries again. Removing a blob the import created and then refused is done with `delete(sha256, only=identity)`, which removes it under the claim only if it is still that file. A refused file is a `REFUSED` result with the validator's reason, and nothing is recorded. When the store already held these bytes, the existing blob is re-hashed first, and one that no longer matches its name raises `BlobIntegrityError` instead of being recorded. Only a failure to open or read the source is a refusal (`unreadable`); a failure of the blob store (its folder cannot be written, the disk is full) is the vault's and propagates. A malformed request (a field `import_sources` would refuse, such as an empty `original_path`) is a `ValueError` before the file is copied, so it leaves no blob; a test ties each CHECK on that table to a request that breaks it. A crash or a database error between the copy and the commit can leave a blob that no row uses. At start-up, after the blob store's own recovery and the migration and before the first request, `vault.ingest.orphans.sweep_orphans` compares every blob with the `blobs` table by hash (never by file name or extension) and moves each one without a row to `blobs/orphans/` with `BlobStore.set_aside`: unchanged, still read-only, on the same volume, and never deleted, so a wrong verdict is undone by moving the file back. A name already taken there is kept and the new one gets a numbered name (`<hash>.<ext>.1`). A link, a junction or a file where the orphan folder belongs is refused, entries the scan does not count as blobs (links, one hash under two names) are only counted, and a blob that cannot be moved is counted and left in place, so start-up goes on. The log line `blobs.orphans` carries three counts and no hash. The importer does not log: the file's name, path and folders go into `import_sources` only.

## Uploading a file

`POST /api/imports/upload` (`vault/api/imports.py`) imports one file sent as the request body (`application/octet-stream`); the page sends one request per file. The name goes in `X-Vault-Filename`, percent-encoded UTF-8 (`encodeURIComponent`), and the optional `X-Vault-Batch` (a ULID) and `X-Vault-Last-Modified` (milliseconds since 1970) in headers too, so a file name is never part of an address. The answer is `{outcome, batch_id, document_id, reason}`; the first file of a batch goes without `X-Vault-Batch` and the rest send the `batch_id` it got back. A name with an extension the vault does not take is refused before the body is read. The body is written to a staging file in the blob store's temporary folder (removed after the import, and by the start-up clean-up after a crash), with the size limit applied to `Content-Length` and again while writing (413). Every disk call (staging, each write, the final `fsync`, the removal) runs in a worker thread, with at most 1 MiB of the body waiting in memory, so a large upload does not hold up the event loop that answers the page's other requests. At most two uploads are staged and imported at once (`UPLOAD_SLOTS`); further uploads wait for a slot before their body is read, holding no worker thread and no staging file, so many files sent together cannot fill the thread pool that also answers the page's other routes. A refused file is a normal answer with the validator's reason; a malformed header is a 400 whose message is fixed text and never repeats the value, and a missing `X-Vault-Filename` (required in the API schema, so generated clients must send it) is FastAPI's 422 naming only the header; without a vault the endpoint answers 503. Like every `/api` route except health it needs the token, and a same-origin `Origin`.

## Document list

`GET /api/documents` (`vault/api/documents.py`, query in `vault.db.documents`) returns one page of the documents in use, or with `trash=true` of the documents in the trash: `{items, total, limit, offset}`. Each item has the document's id, name, extension, media type, size, state, the time it was added and the time it went to the trash (UTC, with a `Z`), and how many imports it has. The name is the file name of its first import (earliest, ties by id), and the size and type are those of its current version. `sort` is `added` (the default), `name` (ignoring the case of ASCII letters) or `size`; `order` is `desc` (the default) or `asc`; every sort ends with the id, so the order is total and the same request on unchanged data gives the same page. `limit` is 1 to 100 (default 50) and `offset` starts at 0. Pages are by offset, so a document added while the owner pages through moves the rest by one. The page and `total` are read in one snapshot (`vault.db.engine.read_snapshot`: the SQLite driver opens a transaction only before a write, so without an explicit `BEGIN` a commit between two reads would show in the second), so they always agree; a page past the end is empty and still gives the total. A document with no import source (which only a hand edit could make) is listed with no name rather than hidden. Without a vault the endpoint answers 503. The names are the owner's file names and are returned to the page only, never logged.

`GET /api/documents/{id}` returns one document, in use or in the trash: the fields of its list item, plus the blob's SHA-256, `local_only`, the current version (id, number, origin), every import source oldest first (file name, original path, folders, file time, method, batch, time of import; the first names the document) and its jobs in the order of the pipeline's stages, each with its status, attempts and the class name of its last error. An unknown id, or a value that is not an id, is a 404 whose message does not repeat it. The reads share one snapshot (`vault.db.engine.read_snapshot`): the SQLite driver opens a transaction only before a write, so without an explicit `BEGIN` a commit between two reads would show in the second.

`GET /api/documents/{id}/file` downloads the document's current bytes exactly as imported, in use or in the trash, always as an attachment (so a browser saves it and never renders it as a page of this origin), under the name of its first import (`<id>.<ext>` when it has none). A name outside plain ASCII, or with a quote or semicolon, goes in `filename*` percent-encoded. The `Content-Type` is the media type the validator gave the file, without a `charset`: a text file may be UTF-16 or UTF-32 with a byte order mark, and Starlette would otherwise add `charset=utf-8`. The bytes are not re-hashed on the way out (a 200 MB file per click); the integrity scan does that. When the stored copy is missing, or two files claim its hash, the answer is a 500 with fixed text and the log records only the event, not the id from the request or the name.

`POST /api/documents/{id}/trash` moves a document to the trash and `POST /api/documents/{id}/restore` brings it back; each returns the document as it now is (the same body as `GET /api/documents/{id}`). The trash is a state (ADR 0005): the document's state goes to `state_before_trash`, `trashed_at` records when (UTC), and nothing else changes, so its file, versions, imports and jobs stay and it can still be opened and downloaded. A restore puts back the state it had and clears both. Each is one `UPDATE` that decides and writes, so it cannot interleave with an import of the same bytes, which also brings a trashed document back (`vault.ingest.importer`). Both are idempotent: trashing a document already in the trash keeps the time it first went there, and restoring one in use changes nothing. An unknown id, or a value that is not an id, is a 404. Like every request that changes something, they need the token and a same-origin `Origin` header. Removing a document for good is the next endpoint.

`DELETE /api/documents/{id}` deletes a document in the trash permanently (`vault.storage.purge`). A document in use is refused with a 409 (`the document is not in the trash`) and nothing changes; an unknown id, including one an earlier request already deleted, is a 404 that does not repeat it. It runs in two steps. First, one transaction removes every row that belongs to the document: its chunks (whose rows in the keyword index `chunks_fts` go with them, by the trigger on deleting a chunk), pages, jobs, import sources and versions, the document itself, and the `blobs` row of each of its blobs that no remaining version uses (a blob another document's version holds keeps its row and its file). `vault.db.documents.DOCUMENT_ROWS` lists those tables, and a test compares it with every foreign key in the schema that points at a document or a version, so a table added later must be added there. That transaction starts with `BEGIN IMMEDIATE` (`vault.db.engine.write_transaction`), so it holds SQLite's write lock while it checks the state: a restore, a move to the trash or an import that lifts the document out of the trash comes wholly before it (the delete is then refused) or wholly after it (and finds no document). Second, after the commit, each of those blobs is removed from the store, deciding again under the write lock that no row names its hash and removing the file under the store's claim on the hash. An import of the same bytes in between records the blob again and keeps it; the importer, for its part, checks inside its own transaction (after its first write has taken the same lock) that the blob's file still exists, and copies the source again if a delete removed it (up to three times). The answer is 204 once the rows are gone. If the process dies after the commit and before a file is removed, or the removal fails (another program holds the file on Windows), the file is left with no `blobs` row, which is exactly what the start-up sweep handles: at the next start it is moved, unchanged, to `blobs/orphans/`. It is not deleted there, because the sweep cannot tell it from an import that crashed before its rows were written, so in that case the bytes stay until the owner empties `blobs/orphans/`. A worker that is running one of the document's jobs loses its outcome (`JobLostError`). The log line `documents.deleted` carries three counts (files removed, kept for a new import, left for the sweep) and no id, name or hash. The plan's vectors and cached AI results do not exist yet; the stages that add them extend this delete.

## Extracted pages

The `pages` table (revision `0004`) holds the text of each page of a document version, as an extractor read it: one row per version and page number, with the text, its length (`char_count`, which the database keeps equal to the text's length), the headings as a JSON list of `[level, title, start, end]` with offsets into the text, the extractor and its version (`text-1`) and the character encoding used, when the format has one. Pages are derived data, rebuilt from the blob when an extractor changes, and as private as the document, so they are never logged. `vault.db.pages.replace_pages` stores every page of a version in one transaction and removes the pages of any earlier extraction, so a reader sees one extraction or the other, never a mixture; `read_pages` returns them in order. Both check the same rules, on the way in and on the way out, because the database can be edited by hand: pages run 1, 2, 3 without a gap, each heading lies inside its page's text, in order and not overlapping the one before, the extractor is a name and a version, and the encoding is a canonical Python codec name (`utf-8`, not `UTF8`). Errors name a page by its number and a heading by its position, never by its text. The database holds a looser form of the same rules (CHECK constraints) and deletes a version's pages with the version. The plan's OCR and page-size columns arrive with the OCR and PDF extractors that fill them. Nothing writes pages yet: the extraction stage that does is a later change.

`GET /api/documents/{id}/pages` (the text view's endpoint, `vault.db.pages.read_current_pages`) returns the pages of the document's current version, in use or in the trash like the details: `{version_id, extracted, extractor, total, offset, limit, pages, next_offset}`, each page with its `number`, `text` and `headings` (`level`, `text`, and `offset`, where the heading starts in the page's text, counted in characters, that is code points, as Python counts them; the page converts). A version holds only its latest extraction, because `replace_pages` replaces every page. Until the version has been extracted the answer is `extracted: false`, `total: 0` and no pages, not a 404, so the page can say so; a new version shows nothing of an older version's text. The response is bounded two ways (plan section 16, "the browser never receives full text except for the page being viewed"): a window starts after `offset` pages (0 to 1,000,000,000) and holds at most `limit` pages (1 to 100, default 20), and it stops before a page that would start past 1,000,000 characters of text (`MAX_WINDOW_CHARS`), except that the first page of a window is always sent whole, however long, so a window never comes back empty before the end. `next_offset` is where the next window starts, or `null` after the last page. The character budget is computed in SQL from `char_count` (a window function over the pages after `offset`), so only the window's texts reach Python. The count, the extractor and the window come from one snapshot; the whole version is checked for one extractor and encoding and for page numbers 1 to `total` without a gap, and each page sent is checked as `read_pages` checks it. Pages that break the rules give a 500 with a fixed message and log the event `documents.pages_invalid` with no id, number or text. Page text is never logged. An unknown id is a 404 that does not repeat it, and without a vault the answer is 503.
## Chunks and keyword index

The `chunks` table (revision `0005`) holds the retrieval chunks of each document version: the version and its document (a foreign key on the pair, so a chunk cannot name another document's version), the chunk's number from 0, its page (`page_start`, `page_end`), its span on that page (`char_start`, `char_end`, offsets in characters into the page's text), the text of that span, the section path (a JSON list of heading titles, outermost first), a token count and the chunker version (`structural-1`). Each page a chunk names must be a stored page of the version, so storing new pages for a version deletes its chunks. The id is an integer that is never reused, because it is what the keyword index, the future vectors and stored citations point at.

`vault.ingest.chunking.structural_v1.chunk_pages` is a pure function from a version's pages to its chunks. It cuts each page at its headings (the section path carries over to the next page until the next heading), splits each section into paragraphs, lines and sentences (a sentence longer than a chunk at white space, a word longer than a chunk into tokens), and packs them into chunks of at most 600 tokens, ending each at the strongest break that leaves at least 400 tokens. When a section continues, the next chunk starts again at the last sentence of the one before if that sentence has at most 60 tokens. Chunks are trimmed of white space, so every chunk's text is exactly `page.text[char_start:char_end]`; a page with no visible text gives no chunk. The plan names no tokenizer, so tokens are approximated (a run of up to four letters or digits, or one other visible character); this, the sizes and the overlap belong to the chunker version, and a change to any of them is a new version.

`vault.db.chunks.replace_chunks` stores a version's chunks in one transaction, replacing any it had. It checks them first against the chunker's rules (numbering, one page per chunk, a non-empty trimmed span, the token count, section titles in the chunker's one-line form) and then, inside the same transaction, against the pages as stored: a chunk whose page is missing or whose text is not that page's text at its span is refused and nothing changes. Errors name a chunk by its number and a page by its number, never by its text.

`chunks_fts` is an FTS5 table over each chunk's text, the document's title and the section path, with the `porter unicode61` tokenizer: case and accents are folded (`cafe` finds `café`), English words are stemmed, and a phrase query such as `"CSE 485"` matches the two words together and in order. Its rowid is the chunk's id. Triggers on `chunks` keep it in step: an insert adds the row, an update replaces it, and a delete removes it, including deletes by a foreign-key cascade (new pages, a deleted document, and the permanent delete, which removes a document's chunks explicitly in its transaction). The title is the name the library shows (`vault.db.documents`): the file name of the document's first import, the earliest by time with ties broken by id. Which import is first can change after the chunks are written (a later import with an earlier or equal time and a lower id, an edited or removed import), so triggers on `import_sources` set the title of the document's index rows again after every insert, update and delete there, touching only rows whose title differs. The migration cannot import the application's query, so it repeats the rule in SQL, and a test checks after each kind of change, and over generated sequences of them, that every indexed title is the name the document list and the detail panel give; a change to the naming rule has to change both. Alembic cannot describe a virtual table, so the migration comparison leaves out exactly the FTS5 table and its shadow tables (`vault.db.schema.FTS_TABLES`), and a test checks that the database holds exactly those. The chunk stage below writes them, and keyword search reads them.

The chunk stage (`vault.ingest.chunk_stage`, the job stage `chunk`) turns a version's stored pages into its chunks. A `chunk` job names a document and, as its input hash, the SHA-256 of the bytes whose pages it chunks; when the document's current version no longer holds those bytes, or the document is gone, the job ends without changing anything. The pages are read in one snapshot and chunked outside any lock, then, in one `BEGIN IMMEDIATE` transaction, read again and compared with the pages that were chunked, headings included: pages an extraction replaced in between fail the attempt (`PagesChangedError`), so it runs again on the new ones instead of storing section paths from headings that are gone. The same transaction replaces the chunks (`vault.db.chunks.write_chunks`, with every check of `replace_chunks`) and makes the document `searchable`, from any state in use (`ready` too, since its new chunks have no vectors yet); a document in the trash stays there and comes back `searchable`. A version with no visible text gets no chunks and is searchable all the same. A version with no stored pages fails the attempt with `PagesMissingError`, and the queue tries again after its back-off. The stage queues nothing after it: `embed` has no handler yet, and a job nothing would claim would show the document as waiting for ever. Nothing queues `chunk` jobs yet either; the extraction stage will, once it stores pages.

## Keyword search

`POST /api/search` (`vault/api/search.py`, `vault.retrieval.keyword`) is the keyword search of plan section 8 (step 3a, and the plain Search page): the body is `{query, limit, offset, types}` and the answer `{items, total, limit, offset}`. The query goes in the body, never in the address, for the same reason as a file name. It is never logged, and every refusal is fixed text.

The query is never passed to FTS5 as query syntax. `build_match` reads it with a small grammar and writes the FTS5 expression itself, with every piece of the owner's text inside a quoted FTS5 string, so `OR`, `NOT`, `NEAR(...)`, `title:` or a stray parenthesis are searched as words and cannot be a syntax error. Text in double quotes is a phrase (an unclosed quote runs to the end); every other word is a term; all of them must match (joined with an explicit `AND`, because FTS5 has no implicit AND next to a parenthesised group, which a test that runs thousands of generated queries against a real index found); a word ending in `*` is a prefix; a code matches with and without its space (`CSE485` is `"CSE485" OR "CSE 485"`, and `CSE 485` typed as two words is `("CSE" AND "485") OR "CSE485"`), as plan section 8 step 2 asks; a word with no letter or digit is dropped, as the tokenizer would drop it, and a query left with no term matches nothing without running. A query is at most 500 characters and 16 terms (422), which bounds the work one request asks of the index.

The scope is applied in the same SQL: documents not in the trash, and only the chunks of each document's current version. Chunks are ranked by FTS5's BM25 over the text, the title (the document's name) and the section path, with equal weights; a document scores as its best chunk. The answer has one item per document: its best chunk, chosen with the title's weight at 0, since every chunk carries the same title and BM25's length normalisation would otherwise pick the shortest chunk for a match by name alone (that match now points at the first chunk) (`chunk_id`, `page`, `char_start` and `char_end` in that page's text, `section_path`), the number of its chunks that match (`matches`), its `name` and `extension`, and a snippet of about 24 tokens of the chunk's text. Items are sorted by the document's score, then by document id, so the order is total and paging is stable; `total` counts the matching documents. `types` limits the search to documents of those extensions (the validator's canonical ones; empty means all). Counting, the page and the snippets are read from one snapshot.

The snippet is a list of segments `{text, match}`. FTS5's `snippet()` marks the matched words with markers made at random for each request (private-use characters around 128 random bits), so a document's own text cannot pose as a highlight, and the page renders the segments as text, never as markup. The name and every section title come back marked the same way (`name_highlight`, and `section_highlight` with one list of segments per title), because the query also searches them: a result found by its file name or its section alone shows where it matched, while its text snippet has no mark (for a match by name alone the snippet is the document's first chunk, since every chunk then scores the same and ties go to the lowest id). The section titles are marked by FTS5's `highlight()` in the stored JSON list and are used only if the list reads back as exactly the stored titles once the marks are removed; otherwise they come back unmarked. A section path in the database that is not a list of titles (an edit by hand) is a `ValueError` with fixed text. Nothing writes chunks yet, so until the chunking stage exists the search finds nothing in a real vault; the tests store pages and chunks themselves. Every query reads every matching chunk to rank it, which is fine at the plan's sizes and is to be measured with the real vault.

## Job queue

Background work is a `jobs` table in `vault.db` (revision `0003`, ADR 0005), driven by `vault.jobs.queue.JobQueue`. A job is one stage (`extract`, `ocr`, `metadata`, `chunk`, `embed`, `enrich`) for one document and its input hash. `enqueue` adds the same document, stage and input only once while it is queued or running (a partial unique index). `claim` hands the most urgent ready job to one worker in a single `UPDATE ... RETURNING`, so two workers never get the same job (a test runs six threads with their own connections). `fail` stores only the exception's class name, never its message, which could quote the document, and queues the job again after 30 seconds, then 1, 2, 4 minutes and so on up to an hour, until its attempts (3 by default) are used up and it is `failed`. `retry` gives a failed job fresh attempts. At every start, before anything else uses the database, `recover` queues again every job that a killed process left `running`, or fails it if that was its last attempt, so a crash loses nothing. The database also checks the job rows: a running job has an owner and no other job has one, a finished job has a finish time, and attempts stay within their limit.

`vault.jobs.worker.WorkerPool` runs the jobs. Each stage with a handler gets as many threads as its limit (`[workers]` in `config.toml`: extraction 2, OCR 1, metadata 1, chunking 1, embedding 1, AI enrichment 2, each from 1 to 16), so a stage never runs more jobs at once than its limit. Each thread claims under its own worker id, runs the handler, and completes the job, or records the failed attempt through `fail`. Every exception is caught, `BaseException` included, because one that left the thread would end it and Python's thread hook would print its message. When the queue says the job was taken back (`JobLostError`), the outcome is dropped. When the database fails while a result is reported, the job stays `running` and the next start-up recovery queues it again. A stage with no handler is never claimed. An idle thread sleeps until `wake()` or for 5 seconds (which is how a job whose back-off has ended is found), so it never spins on the database. `pause()` stops claiming and lets running jobs finish, and `resume()` undoes it. The app starts the pool with the server, after start-up recovery, and on shutdown `stop()` waits up to 10 seconds for running jobs. The pool logs only stage names, counts and outcomes, never a job id, a document id or an error message. Only the chunk stage has a handler so far, so the pool starts one thread; the jobs of the other stages wait in the queue.

## Logging

Use `vault.core.logging.log_event` and `timed`, never a bare `logger.info("... %s", text)`. Logging is deny by default: event names are literals like `ingest.chunk_done`, field names are `lower_snake_case`, and a field value is written only if it is a boolean, `None`, an enum member, a `Metric` or an `Identifier`. Every other value, including every plain `str`, `int` and `float`, is replaced by `[redacted]`. Create a `Metric` with `metric(...)` only from a number the application computed (a count, a size, a duration), never from a number read out of a document. Create an `Identifier` with `identifier(...)` only from an id the application generated (`doc_9f3a1c`, a content hash, a UUID), never from document text or a file name. A logger name is written only if it is an imported module's name (use `logging.getLogger(__name__)`), and the formatter never raises, because Python prints the raw message when a handler fails. Exceptions are logged as type and location only. Third-party loggers are deny by default too: only `uvicorn` and `uvicorn.error` messages are written, any other library's record is written as `message_omitted`, and the server runs with `access_log=False` because uvicorn's access log writes request paths and query strings.

## File validation

`vault.ingest.validate.validate_file(path)` decides whether a file may be imported, before anything parses it: it must be a regular, non-empty file within the size cap, its extension must be on the allowlist (`pdf`, `docx`, `png`, `jpg`/`jpeg`, `txt`, `md`; PPTX, XLSX and CSV arrive with Phase 7), and its bytes must say the same thing as its name. The type comes from the content (PDF header, PNG and JPEG signatures, a zip with the DOCX parts, text with no NUL bytes), so a program renamed `report.pdf` or a picture renamed `notes.docx` is refused as `content_mismatch`. Text with a byte order mark (UTF-8, UTF-16, UTF-32) is decoded with the encoding the mark names and refused if it is invalid there, holds NUL or is mostly control characters, since the mark alone says nothing about the bytes after it. A head cut from a longer file may end inside a character; a file that is shorter than the head (or exactly as long) must end on a whole one, so a mark followed by half a character is refused. A DOCX is a zip, so without extracting anything the check also refuses encrypted entries, member names that climb out of the archive, too many entries, a too-large total and a compression bomb (`unsafe_archive`). The zip directory is bounded before `zipfile` is asked to open it, because `zipfile` reads the whole central directory and builds an object per record first: the end-of-directory record (and its ZIP64 form) is read from the last bytes of the file, found the way `zipfile` finds it (Python releases disagree about where the ZIP64 record is: newer ones follow the locator's offset, so a ZIP64 extensible data sector between them is found, and some 3.12 patch releases read only the fixed 56 bytes before the locator, so the validator reads both places and bounds every record it finds, plus the plain record unless a field holds the "see ZIP64" marker; a locator that leads to no record at either place is refused as unreadable), and a claim of more than the entry limit or more than 4 MiB of directory is refused unopened, and names legacy or password-protected Office files as such. The verdict carries a reason and a detected kind only, never the file's name or content, so it is safe to show or log. Only the first 8 KiB are read to recognise a file; a text file that turns binary later is caught at extraction. The sizes in a zip's directory can be understated by a hostile file, so the extractor must still bound what it reads. The check and the copy into the vault are separate reads: the import pipeline validates the copy it keeps, not the original path. The limits (`Limits`, 200 MiB, 2,000 entries, 4 MiB of directory, 1 GiB unpacked, ratio 200) are first choices to tune.

## Text extraction

`vault.ingest.extractors.text.extract(data, markdown=...)` reads a TXT or Markdown blob into one page of text (Tier B, step 7 of `docs/architecture.md` section 7). A byte order mark names the encoding (UTF-8, UTF-16 or UTF-32) and must hold for the whole file; without one the bytes are UTF-8 when they are valid UTF-8 from end to end, and otherwise the owner's fallback code page, `[processing] text_fallback_encoding` in `config.toml`: Windows-1252 by default, which is what Notepad saved as "ANSI" on an English or Western European system, or another Windows code page (`cp1251` for Cyrillic, `cp932` for Japanese; any other value stops start-up). That is a fixed rule, not detection: the result records the encoding used, and a file in a code page other than the fallback decodes to wrong letters. Detection was tried and left out because charset-normalizer read short Western notes as Central European (`crème` as `crčme`) with full confidence. The whole decoded text must pass the validator's text rule (`validate.reads_as_text`, the same function the import check uses on the head), so a file that turns binary after its first 8 KiB is refused here with `NotTextError`. Line breaks are stored as `\n`; nothing else is changed, and heading offsets are positions in that stored text. Markdown headings come from markdown-it-py's CommonMark parser (ADR 0018), taking only top-level headings: `#` lines and `===`/`---` underlined paragraphs. A YAML front matter block is skipped first, and the parser skips fenced and indented code, HTML blocks, block quotes and list items. markdown-it-py departs from the specification on link reference definitions (`[ref]: /url` followed by an underline gives no heading); a test records each known case. Errors are fixed text and never quote the file. The result names the extractor version (`text-1`) for the hash chain. Nothing calls it yet: the worker pool and the pages table exist, and an extraction handler that runs it on imported TXT and Markdown files and stores its page is the next change.

## Blob store

`vault.storage.blobs.BlobStore` owns the vault's `blobs/` folder (ADR 0006). `put` copies a file's bytes to `sha256/aa/bb/<hash>.<ext>`, hashing as it copies, and marks it read-only; importing the same bytes again (under any extension) stores nothing and says so (`created=False`) and returns the stored blob's real path, and several imports racing for the same bytes, even under different extensions, still produce one blob and exactly one `created=True`: each import takes a claim on the hash (a lock file in `blobs/.tmp/`) while it publishes, because the extension is part of the file name and a link or rename alone cannot make `<hash>.txt` and `<hash>.md` collide. If something that is not a blob (a folder, say) sits where the blob belongs, `put` raises `BlobIntegrityError` and leaves it alone. Only real files and real folders are part of the store: a symbolic link, junction or other reparse point where a blob or one of its `sha256/aa/bb` folders belongs is never read as a blob, never chmodded, published into or deleted through (an import would otherwise alter a file outside the vault, which ADR 0006 forbids), `put` raises `BlobIntegrityError` for it and `scan` reports it. The check is made on each level just before use, so it protects against a damaged or hand-edited store, not against a process racing the store; the vault folder itself may be a link. The same holds for `blobs/.tmp`: a link there stops the start-up with `BlobIntegrityError` instead of letting the clean-up delete files in another folder. A file with another name (a hard link to a file outside the store, which has the same bytes and the same permissions) is not a blob either, since marking it read-only would change the outside file: it is not found, not sealed, reported by `scan` and refused by `put`. A copy is written to `blobs/.tmp/`, flushed, linked to its final name and only then marked read-only, so a crash or a failing source leaves a temporary file at worst (application start-up runs `clean_temp()`, which removes them and any lock a crash left, and then `seal()`, which makes any blob read-only that a crash between publishing and marking left writable, before the first request (a blob counts as sealed only when its mode is exactly `0o444`, so a write bit of the group or anyone else, an execute or set-id bit, or a missing read bit is repaired too, and a repeated import repairs it the same way); the order matters because a blob a crash left linked to its temporary copy has two names until the clean-up removes one), never a partial blob. `max_bytes` stops an oversized file while it is being read. The extension is lower-case letters and digits only and the hash is 64 lower-case hex characters, both checked with `fullmatch`, so nothing a caller passes can change the path. A hash has at most one blob: if a restored or hand-edited store holds `<hash>.txt` and `<hash>.md` side by side, `find`, `open`, `verify` and `put` raise `BlobIntegrityError` instead of picking one, `scan` reports both as strays and trusts neither, and `delete` removes every blob under the hash before it returns `True`, so a deleted document cannot stay readable under the other name. `verify` re-hashes a blob, `scan` lists the blobs and every entry under `sha256/` that is not one (for the integrity check), and `delete` is the one place a read-only original is removed (if the removal fails, the blob is made read-only again before the error is raised). Because a permanent delete runs while the app serves, a look-up whose folder a delete has just removed finds nothing instead of failing, an `open` of a blob removed after its look-up raises `BlobNotFoundError`, and a copy whose `aa/bb` folders a delete of another blob with the same prefix has just removed makes them again. `scan` skips only the folders of the layout (`aa`, `aa/bb`, two hex digits each); any other folder, a folder where a blob belongs (even one named like a blob) and any link is reported as a stray and not entered. It never logs a file name or any content. A dedupe trusts that a stored blob is intact: finding damage is `verify`'s job, and repairing it is a restore from backup.

## Integrity check

`python -m vault.check` (`vault.check`, run by `vault.ps1 check`, plan section 17) checks the vault the settings name and changes nothing. It runs `PRAGMA integrity_check` and `PRAGMA foreign_key_check` on `vault.db` and, if it exists, `index.db`, each opened read-only (`mode=ro` in a `file:` URI built by `Path.as_uri`, so a `%` or `#` in the folder name cannot open another file, and a missing database is reported instead of created). It re-hashes every blob with `BlobStore.verify`, sorts what `BlobStore.scan` reports as not a blob with `BlobStore.stray_kind` (`link`, `hard_link`, `duplicate` for one hash under several names, `other`), and compares the database with the store by hash: versions whose blob is missing, blob rows with no file that no version uses, blobs no row records (the start-up sweep's own rule, `vault.ingest.orphans.unrecorded`, which the sweep and the check share) and blobs with a row that no version uses. A hash under two names or held by a hard link is reported once, as that, not again as a missing blob; a link in a blob's place is never the blob, so its version is reported as missing too. Nothing is sealed, migrated, moved to `blobs/orphans/` or deleted. It can run beside the server: the database is in WAL mode, so the check reads one committed snapshot without blocking it, and every difference between the store and the database, and every odd entry, is looked at once more after the first pass, so an import that finished in between is not reported (one still copying at the end can be, until the check is run again). The report holds counts, a fixed description and code per problem kind (`[blob_mismatch]`) and, for blob problems, up to 20 content hashes per kind; never a file name, a path, a document name or a message from a library. An error this package owns prints its fixed text, any other only its class name. Exit codes: 0 nothing wrong, 1 a problem found, 2 the check could not run. A future `index.db` with sqlite-vec tables will need the extension loaded for its integrity check; nothing creates `index.db` yet.
## Backup

`python -m vault.backup --to <folder>` (or with the folder in `VAULT_BACKUP_TO`, which is how the launcher passes it) backs up the vault named by the settings into a folder outside it, as section 17 of the plan describes. The work is in `vault.storage.backup`:

- The target holds one shared blob store and a folder per snapshot: `blobs/sha256/aa/bb/<hash>.<ext>`, `snapshots/<UTC time as 2026-10-17T143005Z>/vault.db`, `snapshots/<time>/local-token` and, if the settings come from a file, `snapshots/<time>/config.toml`, plus `backup.lock`. Retention (the plan's 14 daily and 12 monthly snapshots) is not implemented: every snapshot is kept until the owner deletes it.
- The database is copied with SQLite's `VACUUM INTO` into `vault.db.partial`, which reads one consistent snapshot while the app goes on writing (a test takes one while another connection commits pairs of rows, and one while a write is uncommitted). The copy is flushed, must pass `PRAGMA quick_check`, and is published as `vault.db` only after every blob it lists is in the target, so a snapshot folder with a `vault.db` is complete. The copy is a plain rollback-journal file that opens read-only without side files.
- Only the blobs the snapshot lists are copied, and only those not already in the target (a blob already there is kept; its size is compared with the record, and the full re-hash is left to the integrity check and the restore). Each is copied with `BlobStore.put(expected_sha256=...)`: to a temporary file in the target, hashed as it is written, flushed, published under its final name only if the hash is the one it is filed under and the byte count is exactly the size its record gives (`BlobMismatchError` otherwise; `max_bytes` alone is only a ceiling, so a shorter copy would pass), and marked read-only. A blob the vault no longer holds, one whose bytes or record do not match, one that cannot be read, and a copy in the target of the wrong size are counted, the rest go on, and the run exits with 1.
- `local-token` is copied into each snapshot, as ADR 0016 says ("backed up with the vault"), so a restored vault keeps the token the browser holds. It is read without following a link (a link, a junction or a folder in its place is refused, and the file opened must be the entry that was checked), written owner-only from the start and left read-only for its owner alone (`0o400`; on Windows the target's access list, which the whole-tree check below covers). It must also be a token by the rule start-up uses (`vault.core.security.parse_token`, shared by both), or no snapshot is made: a restored vault with an empty, cut or garbled token would not start. A vault that has no token yet (the server has not started) is backed up without one, and the output says so. `index.db`, `derived/`, `logs/` and `backups/` are not copied: the app rebuilds them.
- Nothing is overwritten: a snapshot folder is made only if its name is free (two runs in the same second: the second is refused), and published files never replace an entry. A run that fails removes what it wrote into its snapshot folder; a killed run leaves temporary files and unsealed blobs, which the next run removes and seals (`clean_temp()`, `seal()` on the target's store), and a snapshot folder without `vault.db`, which the next run counts and leaves for the owner. A snapshot's own files are published the same way (linked to their final name, the temporary name removed, then made read-only), so a kill in between leaves a `vault.db`, `config.toml` or `local-token` that is published but still writable, perhaps still linked to its temporary name: before it writes, every run removes such a second name and gives every published file of every snapshot, complete or not, exactly its mode (`0o444`, the token `0o400`), refusing a link in a file's place or a file with another name outside it (a hard link) and never entering a linked snapshot folder. Two runs on one target take turns through an operating-system lock on `backup.lock`, released when the process ends however it ends.
- The target must be an absolute path outside the vault folder (judged by the path given and by where a linked vault folder resolves) and outside every Git working tree, by the path given and by the one the system resolves it to (a `subst` drive or a short 8.3 name can put a folder inside a repository under a path outside it). A symbolic link, a junction or another reparse point at any level of the target path, or where `blobs`, `snapshots`, a blob folder, the temporary folder or the lock file belongs, is refused, as the blob store refuses one in the vault.
- On Windows a new or empty target is made private to its owner with the vault's own access-list code (`acl.secure_vault_folder`), and after the backup has written, every file and folder below the target is checked with the vault's start-up walk (`acl.verify_tree`, links listed but not followed): a folder or file moved in keeps its own access list, and new snapshots and blobs inherit the list of the folder they are written into, so a private target folder alone says nothing about `blobs/` or `snapshots/`. The backup counts as private only if the folder and the whole tree are. One that is not (an existing folder with files, an open subfolder or file anywhere below it, or a drive such as exFAT that keeps no permissions) gets a warning, not a refusal: the plan protects an external drive with BitLocker. The walk reads one access list per file, so it takes longer as the backup grows, as the vault's start-up check does.
- The output is counts and the snapshot's name, which the package built. No file name, hash or folder is printed, the target included; errors are fixed text, an error the package does not own is shown by its class name only, and a malformed command line is refused without repeating it.
