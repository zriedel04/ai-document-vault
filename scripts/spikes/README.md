# Phase 0 spike scripts

Measurement scripts for the hardware-dependent decisions in [ADR 0004](../../docs/decisions/0004-sqlite-instead-of-postgresql.md) (sqlite-vec), [0013](../../docs/decisions/0013-embedding-model.md) (embedding model), [0014](../../docs/decisions/0014-ocr-engine.md) (OCR engine) and [0015](../../docs/decisions/0015-pdf-extraction-quality.md) (PDF extraction). **They are run on the owner's Windows PC, never on another machine as a substitute.** CI runs only the unit tests, which use fakes and measure nothing.

Nothing here has been benchmarked yet. The numbers will come from the owner's PC once its specifications are shared.

## What the scripts record

Metrics only: counts, rates, timings, scores. A report cannot hold document text: `Report.add` accepts only numbers and booleans, and names are checked against strict patterns. Console output is built from the same report, so extracted and OCR text, file names and paths are never printed or stored; the last line names only the two files written (`embedding-<candidate>-public.json` or `-private.json`, and `.md`), never the `--out` folder, which is whatever the caller typed. Reports are written to `spike-results/` (git-ignored) and the owner decides which numbers go into `docs/spikes/NN-topic.md`.

## Set up (Windows PowerShell)

Install [uv](https://docs.astral.sh/uv/) if `uv --version` is not found (`winget install --id astral-sh.uv`), then open a new terminal. The scripts need Python 3.12; uv downloads it by itself, so a newer Python on the PC (3.13 or 3.14) is not used and does not need to be removed.

```powershell
cd scripts\spikes
uv sync --python 3.12 --extra vec --extra pdf   # add --extra embedding and --extra ocr for those spikes
uv run python -m vault_spikes check             # what is installed, and whether sqlite-vec loads
```

There is no lock file in the repository: the versions that were actually installed are recorded in each report's Environment section. The heavy libraries are extras so that CI never installs them.

**GPU for the embedding spike.** The `torch` that PyPI serves for Windows is CPU-only, so `--device cuda` stops with a message until the CUDA build is installed. Install it with the command from pytorch.org (Get Started, Windows, Pip, CUDA), then run every later command with `uv run --no-sync` so uv does not put the CPU build back. Run the `--device cpu` measurements first, because they need none of this.

## Commands

| Spike | Command | Feeds |
| --- | --- | --- |
| sqlite-vec | `uv run python -m vault_spikes vec` | ADR 0004 |
| Embedding model | first `uv run python -m vault_spikes fetch-model --candidate qwen3-embedding-0.6b` (downloads the model once, not timed), then `uv run python -m vault_spikes embedding --candidate qwen3-embedding-0.6b --device cpu` (then `--device cuda`, and the same two steps for `embeddinggemma-300m`) | ADR 0013 |
| OCR | `uv run python -m vault_spikes ocr --engine rapidocr --images <folder>` (then `--engine tesseract`) | ADR 0014 |
| PDF | `uv run python -m vault_spikes pdf --extractor pypdfium2 --pdfs <folder>` (then `pypdfium2+pdfplumber`) | ADR 0015 |
| Combine | `uv run python -m vault_spikes merge spike-results\embedding-*.json` | one table per spike |

Each process measures one candidate, so memory numbers do not mix, and `merge` joins the reports. The embedding report's name carries the data set (`embedding-<candidate>-public` or `-private`), because ADR 0013 needs the same candidate on both and one name would let the second run replace the first. A run never replaces a report that already exists: it stops before it starts, so a name clash is found before the hour is spent, and you move the old file or pass another `--out`. `merge` is the exception for its own output (a derived file, `embedding.json`, which a later merge may replace), but it refuses to write over one of the reports it was given. `merge` accepts only reports from this script: a report's title, question and method must equal the spike's own text, every candidate, metric and package name must be one that spike can produce (each spike module lists them as `CANDIDATES`, `METRICS` and its packages, so a lower-case word of the right shape, such as a diagnosis, is refused, and the error names the kind of name, never the name), every package version and the Python version must be a version number (numbers with an optional `a`/`b`/`rc`, `.post`, `.dev` or a fixed local label such as `+cu128`) or the word `not installed` or `unknown`, so a word of the right shape cannot carry text into a report (a version found on the machine in any other shape is stored as `unknown`), and every metric value must be of the kind its metric allows (each spike lists the kind of every metric it can emit: a count is a whole number from 0, a ratio such as `recall_at_10` is from 0 to 1, an amount such as `load_seconds` is 0 or more, a flag is true or false, and a boolean is never a number), so `"recall_at_10": -5` or `"load_seconds": true` in a hand-edited file is refused and the error names the metric, never the value, and its machine description (system, CPU, GPU) must be made only of words from a fixed list of operating system, processor and graphics card words (`MACHINE_WORDS` in `report.py`, such as `Windows`, `Ryzen`, `GeForce`, `RTX`) and model numbers (`7800X3D`, `3080`, `i7-12700K`), at most 100 characters, so a hand-edited file cannot carry a sentence or a word of document text into a merged report (`Patient diagnosis confidential` is refused, and so is any name the list does not know). The code that reads the machine never copies a string it cannot vouch for: the system is the OS name and the leading numbers of its release (`Windows 11`, `Linux 6.18.44`), and a CPU or GPU name with an unlisted word is stored as `unknown`; add the word to the list in a reviewed change if a real card or processor shows up as `unknown`. Digits are still digits: a model-number-shaped token such as `123456` passes, which is why the Environment lines are still read before a report is committed. A CUDA run of the embedding spike reports `peak_memory_mib` (the process's peak working set, host RAM) and, separately, `gpu_peak_allocated_mib` and `gpu_peak_reserved_mib` (the most video memory torch allocated and reserved), because the working set does not include video memory and a model that nearly fills the card would otherwise look small. OCR images and PDFs may have a reference text file of the same name (`scan1.png` and `scan1.txt`); the script reports the error rate and discards both texts. A PDF may also have `name.headings.txt`, one expected heading per line: with `--extractor pypdfium2+pdfplumber` the report then gives heading precision, recall and F1 (a count of candidates alone cannot tell good detection from bad, so without such a file no heading accuracy is claimed). An empty `name.headings.txt` says the PDF has no headings, so every heading found in it counts as a false one. Headings are counted once per occurrence, so a running header found on 20 pages is 20 false positives, and a heading expected twice and found once is half found. The embedding spike chunks only the first of a set of exact duplicates (`exact_duplicate_of` in the manifest), as the import pipeline stops at an exact-duplicate match; identical copies would take several of the ten places that Recall@10 and MRR score and push a required passage out. A question may still cite the copy, which counts as the original, and a copy whose original cannot be read is counted with the skipped documents. Retrieval in the embedding spike is scored by passage for Recall@10 and MRR: a chunk counts only if it comes from the right document and holds the whole `quote` of the eval file (half a quote is not the passage), and the report counts required passages that no chunk holds at all. So that a boundary cannot cut a quote in two, the chunks overlap by at least the longest quote in the eval file (a quarter more, within 100 to 400 characters; the overlap used is a metric of the report, `chunk_overlap_chars`, and the same for every candidate), and a quote longer than that which still falls across a boundary shows up in the count of passages no chunk holds. Hit@1 is scored by document, as the architecture plan defines it, and only for the questions the eval file marks `find_document: true` (the plan defines it for "find the document" questions, not for every factual question whose answer happens to lie in one document; the mark is never guessed from the category, and the loader refuses it on a question that is unanswerable or needs several documents): it asks whether the top chunk comes from a document that holds the evidence, and the report gives how many questions it covers (`hit_at_1_questions`). If no question is marked, `hit_at_1` is left out instead of reading as 0. The eval file's question ids must be unique and non-empty (scores are kept per id, so a repeated id would score two questions with one ranking), and the loader refuses a file that repeats one. A document the script cannot read (an encrypted or corrupt PDF, a damaged DOCX) is skipped and counted with the scans, not a reason to stop the run. A question is scored when every passage it needs is in a document the script could read, or, for a question that needs one passage, when one of its `alternatives` is (a scan whose answer is also in a text file stays in, as the score already gives an alternative full credit); the other answerable questions are counted in `questions_left_out`, and a passage in a document that could not be read is not counted in `sources_not_in_any_chunk`, which is for quotes that a readable document should hold and no chunk does. For a question with one required passage that count asks whether any acceptable passage is held (the required one or an alternative, as the scorer gives either full credit), so a question scored through an alternative because its scan is unreadable shows a mistyped alternative there instead of lowering Recall and MRR unnoticed. The sqlite-vec report records `queries_timed`, the number of searches its p50 and p95 rest on. Its exact-search check compares the extension's answer with a plain-Python search place by place, so the right ten neighbours in the wrong order (farthest first, for example) fail it; a neighbour is accepted in place of the exact one only when its distance is equal within float32 rounding (a tie), and a repeated id, a missing id or an id outside the data fails. The embedding report also records the `batch_size` it used (a whole number from 1, refused otherwise, as are `--vault-chunks` and the other size options), because batch size changes throughput and memory and rows measured with different batches do not compare. The script passes the same batch size to the encoder (sentence-transformers batches by 32 unless told otherwise, so a run asked for 64 would otherwise have been measured at 32 and reported as 64), and leaves precision and the maximum sequence length at the library's defaults. `merge` also checks the shape of every row, per candidate: each row must carry the metrics every row of that candidate has (`public_dataset`, `documents_skipped`, the counts of what was measured) and may carry only the others it can emit (video memory only for a `-cuda` embedding run, a peak memory figure for RapidOCR but not Tesseract, heading scores only for `pypdfium2+pdfplumber`, the size figures only on a `vectors-N` row); an empty row, a row without its context and a row with another candidate's figure are refused, and the error says which kind of fault, never the name. The manifest loader refuses an `exact_duplicate_of` that names a document the manifest does not list, the document itself, or a loop, and the corpus builder compares the bytes of the copy with its original (size first, then SHA-256) before it drops the copy, so a mislabelled file stops the run instead of being left out of the corpus and scored against another document. The manifest loader refuses a document listed twice, counting spellings Windows treats as one file (case, the kind of slash, a leading `./`), because a file chunked twice would take several of the ten ranked places. The chunks of the embedding spike are plain windows of at most 800 characters (about 200 tokens), not the structure-aware chunks of 400 to 600 tokens with the title and section path that `docs/architecture.md` plans for the application (the chunker is not built yet): the comparison of the candidates holds for this representation, and chunks per second and the projection for a vault of N chunks hold for chunks of this size, so they are not to be read as the application's figures. The OCR spike reports `peak_memory_mib` only for an engine that runs inside the process (RapidOCR): Tesseract runs as a separate program for each image, so this process's working set would be the wrapper's, and its memory is read in Task Manager while it runs. `documents_skipped` is the number of documents the script could not read (scans, pictures, damaged files, and a copy whose original could not be read), so a good score can be read next to what was left out. The GPU name found after an embedding run is stored in the same fixed vocabulary as the CPU (`unknown` if the card name has a word outside it), so a card such as `NVIDIA RTX 4000 Ada Generation` cannot discard a finished measurement. `merge` keeps each candidate's own environment: the documented order runs the CPU candidates, then swaps the CPU-only torch build for a CUDA build, so a merged report lists both environments by candidate instead of showing the first one for every row. The embedding spike defaults to the public synthetic corpus in `demo/corpus/` and the public eval set in `eval/public/`, which arrive with the demo corpus pull request (until then it stops with a message and you pass `--corpus` and `--questions`); point `--corpus` and `--questions` elsewhere to run on private files, which must stay outside the repository. The report's `public_dataset` metric is 1 only when both paths are the repository's own `demo/corpus/` and `eval/public/questions.yaml`; anything else, including a copy with the same names, is reported as 0, so a report always says what its numbers were measured on. The RapidOCR engine is configured explicitly with the PP-OCRv5 mobile detection and recognition models, because the package's own default is PP-OCRv4 before release 3.9 and PP-OCRv6 from 3.9 (checked in the packages' `config.yaml`), and the extra requires `rapidocr>=3.4`, the oldest release checked with those settings; the first run downloads the models. The Tesseract version is stored as the bare number (`5.5.0`), and a first line with no number is stored as `unknown`.

## From a report to a spike file

Each report is written as JSON and as a Markdown draft with the five sections `scripts/check_adrs.py` requires. The Conclusion is a placeholder on purpose. The owner reviews the numbers, copies the draft to `docs/spikes/NN-topic.md`, writes the conclusion and only then links it from the ADR. See [docs/spikes/README.md](../../docs/spikes/README.md).

## What these scripts cannot show

The unit tests prove that the measurements are computed and recorded correctly with fakes. They do not prove that the sentence-transformers, RapidOCR and Tesseract adapters run on the PC: their first real run is the first test. If an adapter fails there, that is a bug in the script, not a result about the technology.

## Checks

```
cd scripts/spikes
uv run --with pyyaml python -m unittest discover -s tests -v
uvx ruff check . ; uvx ruff format --check .
uvx --with pyyaml --with types-pyyaml mypy
``` The command line prints a failure in full only when it is one of this package's own errors (`OwnValueError`, `OwnTypeError`, `OwnRuntimeError`, `SpikeInputError`, `MissingDependencyError`, whose messages name no file and quote no document, and a test fails if any module raises a plain `ValueError`, `TypeError` or `RuntimeError`); any other exception, such as a missing or unreadable input folder or a library's own error, is reported as one line with its class name only and exit code 1, because Python's message and traceback would carry the path of a private folder or file or a piece of a document.
