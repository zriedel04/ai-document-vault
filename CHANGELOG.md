# Changelog

All notable changes are recorded here, following [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added

- Cloud egress gate (`vault.ai.egress.check_egress`; plan section 10, ADR 0010), ahead of Phase 5 and not yet called by anything: takes the chunk ids about to be sent to a cloud model and returns the ones that may be sent, in input order and each once, and the ones withheld with a reason (unknown chunk, missing document, in the trash, document Local Only, a Local Only label on the document or above one of its labels, database error). The caller picks `DROP` (send the rest) or `REFUSE` (send nothing if anything is withheld) on every call. It fails closed and logs only counts and chunk ids.
- Citation validation (`vault.answers.citations`; plan section 11, ADR 0011, the validator of Phase 5): the session's labels `S1` to `Sn` made by the server for the passages sent, a strict schema for the model's structured answer (segments with labels and a quote, `insufficient_evidence`, `missing`) that refuses unknown fields, wrong kinds, repeated keys and oversized input with fixed text, and `validate_answer`, which resolves each label to the chunk, version and document ids and pages, checks each quote within one cited passage after a narrow documented normalisation (NFC, quotation marks, dashes, white space runs), matching only whole extended grapheme clusters (`vault.answers.graphemes`, UAX #29 for Unicode 15.0.0, tested against Perl's `\X`) and returns each segment as uncited, unsupported (any invented label), supported or unverified, by that precedence, with typed fixed-text findings (invented or repeated label, uncited segment, missing quote, quote not found, empty segment, empty answer, the flag with claims or without a note). No provider, prompt or dependency yet.
- Language model provider interface and fake provider (`vault.ai.providers.base`, `vault.ai.providers.fake`, `vault.ai.answer`; plan section 9, Phase 5, ADR 0009): the provider-neutral `LLMRequest`, `LLMResponse`, `Usage`, streaming events (`TextDelta`, then one `Completed`; closing the generator cancels it), the `LLMProvider` protocol and `LLMError` with six fixed-text kinds, all checked when built; `parse_structured`, one strict JSON rule for structured output; the cited-answer shape of ADR 0011 (`CitedAnswer`, `ANSWER_SCHEMA`, `read_answer`); and an offline, deterministic `FakeProvider` that answers in that shape from the sources it is given. A contract suite runs through a parametrised fixture that holds only the fake for now, so the Anthropic and OpenAI adapters can join it unchanged. No SDK, key, network access, routing config, egress gate or prompt yet.
- Manual collections and tags (plan section 12, SHOULD HAVE; section 6 labels and resolution order): `POST /api/labels` makes a `collection` or a `tag` at the top or under a label of the same kind, `PATCH /api/labels/{id}` renames and moves it (a move under itself or a label below it, deeper than 64 levels, or into a name already there is a 409), `DELETE /api/labels/{id}` deletes it with its assignments (the documents stay; a label with labels under it is a 409), and `PUT` and `DELETE /api/documents/{id}/labels/{label_id}` assign and unassign it as the owner's own (`source` user, accepted; an assignment from another source stays). Names are cleaned as folder names are (`vault.ingest.path_metadata.owner_label_name`) and refused (422) when nothing or more than 255 characters are left, and compared as Windows compares them, unique per kind and parent. Folder labels stay the imports': every one of these routes refuses them (409). The existing `label` filters of `GET /api/documents` and `POST /api/search` work for the new labels unchanged. The document page has a **Collections and tags** section (`frontend/src/pages/OwnerLabels.tsx`): the owner's labels on the document with Remove, a list to add one, and a field to make a new collection and add the document to it, under the page's one mutation lock with trash, restore, delete and retry; the new labels appear in the Label filters. The label request bodies refuse unknown keys (`RequestBody`). No migration: `labels` already allows both kinds
- Per-page OCR detection for PDFs (plan section 7, step 8; Phase 3), without an OCR engine (ADR 0014 stays Proposed): the PDF extractor (`pdf-2`) measures each page in the sandbox (its size, and the glyphs PDFium finds no Unicode mapping for), and the extraction stage decides per page (`vault.ingest.text_layer`) and stores the result in the new `pages.text_layer` column (migration `0008`): `empty`, `unreadable` (fewer than half of the visible characters are letters, numbers or marks), `sparse` (fewer than 10 visible characters per A4 area) or `usable`. Pages stored by `pdf-1` are migrated to `empty` or `unjudged`. The extractor golden files record the measurements and the decision, with a new fixture that has one page for each outcome.
- Vector index `index.db` (`vault.retrieval.vectors`, plan sections 5, 6 and 8, ADR 0004) with sqlite-vec 0.1.9 (MIT or Apache-2.0, a new runtime dependency recorded in ADR 0019; licence text from upstream in the notices): records the embedding model id, dimension count and layout version and refuses another model or dimension count (`IndexModelMismatch`) until the index is rebuilt (`VectorIndex.create`); stores, replaces and deletes vectors by chunk, version or document; exact cosine k-nearest search, nearest first with ties by chunk id, limited to a set of chunks or documents before ranking. A damaged index is removed and made anew without touching `vault.db`; a link, junction or hard link where it belongs is refused. Permanent delete removes the document's vectors, and a start-up sweep removes vectors whose chunk is gone. No embedding stage and no model yet (ADR 0013 is Proposed)
- Reciprocal Rank Fusion (`vault.retrieval.fusion`; plan section 8 steps 4 and 6, ADR 0008), ahead of Phase 4 and not yet used by search: `fuse` merges a keyword and a vector ranking of chunk ids by `sum 1/(rrf_k + rank)` with exact fractional scores and ties in ascending chunk id, counting a chunk repeated in a list once and refusing a chunk given two documents; `cap_per_document` keeps at most M chunks of each document. A new `[retrieval]` config section holds every number (`keyword_candidates` 50, `vector_candidates` 50, `rrf_k` 60, `max_chunks_per_document` 3) as strict whole numbers in bounds, accepting decimal text only from environment variables.
- PDF file properties (`vault.ingest.metadata_stage`, `vault.ingest.extractors.pdf.read_properties`, sandbox entry point `pdf_properties`, `pdf` in `metadata_stage.READERS`): the `metadata` job, now queued by the importer beside `extract` for a PDF too and once at start-up for PDFs imported before, reads the document information dictionary (`Title`, `Author`, `CreationDate`, `ModDate`) with pypdfium2 in the sandbox, opened exactly as the PDF extractor opens it (a PDF that needs a password or cannot be parsed fails the attempt as extraction would; an owner-password-only PDF is read). PDFium decodes UTF-16BE after its byte order mark and PDFDocEncoding, and the tests pin every one of PDFDocEncoding's 256 codes against the standard's table. The server judges each value as a DOCX's: names cleaned and cut to 255 characters, dates accepted only as strict PDF dates (`D:YYYYMMDDHHmmSSOHH'mm'`, ISO 32000-1 7.9.4) and stored in the DOCX dates' forms; a time without a zone (ambiguous), a malformed or out-of-range date and a value over 65,536 UTF-16 units are left out without failing the job. XMP metadata is not read. The values are never logged. ADR 0015 stays Proposed: this is a first version on pypdfium2.
- Import date filter on search: `imported_from` and `imported_to` on `POST /api/search`, both optional and inclusive, the documents whose first import (`documents.created_at`) falls between two instants given in RFC 3339 with an explicit offset, applied in the same statement as the other filters so totals, ranking and paging count only those documents; a bound that is not such an instant, is outside the years 1 to 9999 in UTC, or starts after the end is a 422 that names the field and never repeats the value. The Search page has **Imported from** and **Imported to** date fields, kept in its state and never in the address, and sends the first and last instant of the chosen days in the browser's own time zone (rule in the notes table of `docs/architecture.md`).
- Type and state filters for the library: `GET /api/documents` takes `type` (a canonical extension, as `POST /api/search` takes it) and `state` (`processing`, `searchable`, `ready`, `failed`; in the trash, the state a document had when it went there), each repeatable and combined with the label filter, the trash flag and paging in one statement, so `total` counts what passes them all. An unknown value is a 422 with fixed text that does not repeat it. The Documents page offers Type and State checkboxes and keeps the checked values in the address as fixed tokens only (`parseDocumentsSearch` falls back to every value for anything else), so a failed document can be found and retried.
- Extractor golden-file tests (plan section 13, Phase 2 testing): a fixture set built in code (`backend/tests/unit/extractor_golden.py`; no binary committed) for the TXT, Markdown, DOCX and PDF extractors, covering two-column PDFs, DOCX and Markdown headings and tables, right-to-left, CJK and combining marks, an encrypted PDF and an OLE container, and corrupt, truncated and empty files of each type. Each fixture runs through its sandbox entry point as the extraction stage runs it, and its pages, text, headings and offsets (or its error class and reason) are recorded in `backend/tests/fixtures/extractors/`; `uv run python -m tests.unit.extractor_golden` regenerates them and `tests/unit/test_extractor_golden.py` fails when an output drifts.
- Phase 2 end-to-end test (`backend/tests/unit/test_end_to_end.py`): a synthetic TXT, Markdown, DOCX and three-page PDF are uploaded through `POST /api/imports/upload` to an app started with its lifespan, so the app's own worker pool runs extract, metadata and chunk in the sandbox until each document is `searchable`; it then checks that every chunk lies on a stored page of its version and that its offsets slice exactly its text out of that page, that `POST /api/search` finds each document by a phrase and by its course code written apart, joined, in lower case and (for a code written apart) with a hyphen, that each hit names the page holding the passage with a snippet that marks it, and that `GET /api/documents/{id}/pages` opens that page (the plan's Phase 2 exit check and its chunk traceability and code-term tests).
- Title, folders and file properties on the document page: the title with where it came from ("from the file's properties" or "from the file name"), the deepest folder of each import path written out whole (`School › CSE 485`), and the file's author, created and modified dates where the file gives them (a year, month or day shown as such in UTC, a time in the viewer's time zone), all from `GET /api/documents/{id}` and shown as plain text that wraps and keeps its own direction (`src/pages/document-fields.ts`).
- Export manifest: each document's file properties for its current version (`vault.db.fields.NAMES`: title, author, created, modified, as the metadata stage stored them) in `manifest.json` as `file_properties` (exact values, `null` when absent; `format_version` 3) and in `manifest.csv` as `file_title`, `file_author`, `file_created` and `file_modified`, neutralised like every cell. Values recorded against another version are left out, and a vault from before `document_fields` still exports with none. Read in the export's one read-only snapshot.
- Browsing by label: `GET /api/labels` lists every label as a tree (each with its parent, path and the documents not in the trash that carry it or a label below it), and a `label` filter on `GET /api/documents` and `POST /api/search` keeps the documents under a label, the label and every label below it, in the same SQL as the rest of the scope, so totals, ranking and pages stay correct. The Documents page offers it as a **Label** choice (the label's id in the address) and the Search page beside the types (in component state only). An unknown label is a fixed 404; names are rendered as text and never logged.
- PDF extraction in the job pipeline: the extraction stage runs the PDF text extractor (`pdf-1`) in the sandbox (`pdf` in `vault.jobs.sandbox.ENTRY_POINTS` and in `extract_stage.EXTRACTORS`, its version tied to the extractor's by a test), so an imported PDF is extracted, chunked and found by keyword search instead of waiting in the queue. A page with no text layer is stored empty and the document completes (`searchable`; a scan has no chunks until the OCR stage of Phase 3); a PDF that needs a password, has no pages, is over a cap or cannot be parsed fails the attempt as `SandboxChildError` with nothing of the file in the job, the log or the console; an answer with headings, which `pdf-1` never finds, is refused. A test runs PDFs at the extractor's caps (5,000 pages, nearly 3 million characters, and a 200 MiB file) within the default sandbox limits. ADR 0015 stays Proposed: this is a first version pending the owner's PDF spike.
- DOCX file properties (`vault.ingest.metadata_stage`, `vault.db.fields`, `document_fields` table, migration `0007`; the file-properties part of plan section 7, step 9): a `metadata` job, queued by the importer beside `extract` for a DOCX and once at start-up for DOCX documents imported before, reads the core properties (title, author, created, modified) in the sandbox (entry point `docx_properties`, after the DOCX extractor's validation and bounded copy) and stores them with `source = file_properties` against the version they were read from. The values are judged in the server: names cleaned as folder labels are and cut to 255 characters, dates accepted only as strict W3CDTF with `xsi:type="dcterms:W3CDTF"` (a time stored in UTC to the second); a malformed, repeated or missing value is left out without failing the job. `GET /api/documents/{id}` returns `file_properties` and resolves `title` as the file's own title, else the file name (`source` `file_properties` or `filename`). The values are never logged. PDF properties wait for the PDF extractor.
- Export manifest: each document's title with its source (`title`, the one the library shows: a DOCX's own title, else the first import's file name) and its labels (`labels`: kind, name, full path, source and status, in the library's order) in `manifest.json` (`format_version` 2) and `manifest.csv` (`title`, `title_source` and a `labels` cell holding the same JSON list, so commas, quotes, line breaks and formula characters stay in the cell). `labels_complete` in `manifest.json`, and a warning from the command, say when the app has not yet labelled the imports of an older vault. The detail panel and the export share `resolved_title` and `label_order`, so they cannot disagree.
- PDF text extractor (`vault.ingest.extractors.pdf`, pypdfium2 5.14, Apache-2.0 or BSD-3-Clause, as ADR 0012 accepts; extraction quality, ADR 0015, is still Proposed pending the owner's spike, so this is a first version on that proposal): one page per PDF page with its text-layer text in PDFium's reading order, `\n` line breaks, words hyphenated at a line end joined, control characters and noncharacters removed, and a page with no text layer (or only white space) stored as empty text for the Phase 3 OCR stage to find; no headings yet. Refused with fixed-text errors that never quote the file: a PDF that needs a password or an unsupported security handler (`EncryptedPdfError`; no password is ever tried, and an owner-password-only PDF is read), no pages (`EmptyPdfError`), more than 5,000 pages or 3 million characters (`PdfLimitError`, checked before each page's text is read and set to fit the sandbox's answer caps in the worst case), and bytes that are too large, not a PDF, unparsable or missing a page (`NotPdfError`). Runs in the sandbox; not wired into the job queue yet. The Python licence check now reads pypdfium2's free-text licence field (`BSD-3-Clause, Apache-2.0, dependency licenses`) as `Apache-2.0 OR BSD-3-Clause` through a `TRANSLATED` table tied to that exact value and to ADR 0012, which must still pass the allowed list, also with `--strict`. The third-party notices list pypdfium2 and the licences of the libraries built into its PDFium, which its Linux and Windows wheels ship under a folder named for the platform (`third_party_notices.PLATFORM_FOLDERS`), with its licence shown as the expression the licence check translates it to.
- Export manifest: each document's title with its source (`title`, the one the library shows, from the first import's file name) and its labels (`labels`: kind, name, full path, source and status, in the library's order) in `manifest.json` (`format_version` 2) and `manifest.csv` (`title`, `title_source` and a `labels` cell holding the same JSON list, so commas, quotes, line breaks and formula characters stay in the cell). `labels_complete` in `manifest.json`, and a warning from the command, say when the app has not yet labelled the imports of an older vault. The detail panel and the export share `resolved_title` and `label_order`, so they cannot disagree.
- Retrieval evaluation `python -m vault.eval` (`vault.eval`, `vault.retrieval.evaluation`): imports the corpus `manifest.json` lists (by default `demo/corpus/`) into a throwaway vault with the product's importer, extracts the TXT, Markdown and DOCX documents and chunks them with the chunk stage, asks each question of the eval file (by default `eval/public/questions.yaml`) through keyword search, the code behind `POST /api/search`, and prints Recall@10, MRR and document Hit@1 with counts of what was indexed, refused at import or left without an extractor and of the questions that could not be scored, which are counted apart instead of scored as misses; `--json` writes the same numbers to a new file. The eval file, the manifest and the scores are the spike scripts' own (`vault_spikes.corpus`, `vault_spikes.retrieval`), installed into the backend's development environment from `scripts/spikes`, which now has a build system and a licence for it. Numbers only: no question, id, path or document text is printed, errors are fixed text or a class name, and a malformed command line is not repeated. CI runs it on the demo corpus (Linux and Windows) and fails only if it cannot run; there is no score threshold yet. On the demo corpus today: 18 questions scored, Recall@10 0.000, MRR 0.000, Hit@1 0.000 over 3, because keyword search requires every word of the question to match. Until the extraction stage is merged, the extractors run in the evaluation's process rather than the sandbox.
- Extraction stage (`vault.ingest.extract_stage`, job stage `extract`, registered with the worker pool): runs the TXT, Markdown and DOCX extractors in the sandbox with the configured limits and fallback code page, checks the blob's bytes against its hash first and the extractor's answer after (its version, an encoding it can report, the page rules), and stores the pages, queues the `chunk` job and completes the job in one transaction, so an imported TXT, Markdown or DOCX file now becomes searchable without further steps. A sandbox failure the document can cause fails the attempt by class name only and is retried; a sandbox that cannot run defers the job without using an attempt (`JobQueue.defer`); a type with no extractor yet (PDF, images) is not claimed and waits in the queue (`JobQueue.claim(..., extensions=...)`). Sandbox entry points can declare options (`EntryPoint.options`), which the text extractors use for the fallback code page. The worker pool wakes after a job ends done and after an upload, so the next stage starts at once. Stored pages now accept heading levels 1 to 9, the range of the DOCX extractor (`Heading 7` to `Heading 9` made extraction fail before).
- Licence audit (`docs/licence-audit.md`) and generated third-party notices (`THIRD_PARTY_NOTICES.md`, `scripts/third_party_notices.py`) for the runtime packages, with CI checks (npm on Linux, Python on Linux and Windows) that the notices list every runtime package, and every installed copy of an npm package, with its current licence text. A package that ships no licence file needs a reviewed upstream text in `scripts/notices/`. Optional npm packages limited to some platforms (the `@napi-rs/canvas` native binaries under pdfjs-dist) are left out, since a browser build cannot include them and npm installs only the current machine's. First written in PR #39, which was merged into an already merged branch and never reached main; regenerated here against the current dependencies. The audit records two open points for the owner: lxml's wheels bundle libiconv (LGPL-2.1), and pdfjs-dist ships Liberation fonts (GPL-2.0 with a font exception) that the viewer does not load or build in.
- Export `.\vault.ps1 export -To <folder> [-IncludeTrash]` (`python -m vault.export`, `vault.storage.export`), the plan's way out of lock-in: every document's current original, checked against its hash and exact size, in a `files/` tree laid out by the folders of its first import (flat for an upload), with `manifest.json` and `manifest.csv` (one row per import source) holding each document's states, versions, import sources, hashes and sizes. Names are made safe for Windows (forbidden and control characters, trailing dots and spaces, device names such as `CON` and `COM1`, 120-unit names) and kept within `MAX_PATH`; documents whose names collide, case-insensitively, are all kept with ` (2)`, ` (3)` in a fixed order. The CSV is UTF-8 with a byte order mark and neutralises cells that would start a formula. The trash is left out by default. Built in a hidden folder beside a new or empty target and renamed only when complete; refuses a folder inside the vault, inside a Git repository or reached through a link or junction (the backup's checks); prints counts only.
- Image viewer on the document page for PNG and JPEG documents: the current version fetched with the token header and shown through a `blob:` address that is released when the page leaves or the document changes, fitted to the width, with **Fit**, **100%**, zoom in and out by steps and **Open image alone**. A file over 32 MiB is fetched only when asked and an image over 50 megapixels is not drawn until asked, so a huge scan does not stall the page. No OCR text overlay yet (Proposed ADR 0014).
- Folder labels and a file-name title (`vault.ingest.path_metadata`, `vault.db.labels`, `labels` and `document_labels` tables, migration `0006`; the deterministic metadata of plan section 7, step 9, for the import path and file name): each folder an import came from becomes a `folder` label nested under the one above it and assigned to the document with `source = import_path`, written in the import's own transaction, so a second import of the same bytes adds its folders too; names are cleaned as untrusted text (NFC, no control or bidirectional characters, white space collapsed, trailing dots and spaces dropped, at most 255 characters and 64 levels), `\` and `/` both separate, a leading drive, UNC share or device prefix is not a label, and names are compared as Windows compares them, so `School` and `school` are one label. `GET /api/documents/{id}` returns the document's labels with their paths and a `title` from the first import's file name with its source. A permanent delete removes the folder labels no other document carries, sources from before the migration are labelled once at the next start, and nothing is logged but counts.
- Restore `.\vault.ps1 restore -From <snapshot> -To <folder>` (`python -m vault.restore`, `vault.storage.restore`): copies a backup snapshot (or a backup folder's newest complete one) into a new or empty vault folder, never over a vault: `vault.db` checked with SQLite's full integrity check, every original file it lists copied from the backup and published read-only only with the hash and exact size its row gives, `local-token` (ADR 0016) and the snapshot's `config.toml`. Works in a `.vault-restore-<random>` folder beside the target that is renamed only when complete, so an interrupted restore never leaves a half vault under the target's name; uses the backup's link, Git, vault-folder and Windows access-list checks; counts missing or damaged files and exits with 1; prints counts only. Queues nothing, since no derived data lives outside `vault.db` yet.
- PDF viewer on a PDF's page in the app (pdfjs-dist 6.3.289, Apache-2.0, through react-pdf 11.0.0, MIT, both pinned): the original one page at a time with Previous, Next and Go to page, opened at the page in the address (`?page=4`; anything but a whole number from 1 opens page 1, a page past the end shows the last with a notice), the bytes fetched once per version through the download endpoint with the token in the header and handed to PDF.js as bytes, the worker built into the app's own files under `script-src 'self'` with no change to the Content-Security-Policy, and no annotation layer, form fields, XFA, WebAssembly, resource fetches, password prompt or console output; other documents keep the text view.
- DOCX extractor (`vault.ingest.extractors.docx`, python-docx): body paragraphs and tables in order (cells separated by tabs, rows by line breaks, paragraphs by a blank line), tracked changes read as accepted (co-authoring conflicts too: `w14:conflictDel` left out, `w14:conflictIns` kept), text boxes read once (the first alternate content choice whose required namespaces it understands, else the fallback), a file with content imported from another file (`w:altChunk`) refused rather than read in part, Markup Compatibility applied as the standard asks (elements of a namespace declared `mc:Ignorable` and not understood left out unless `mc:ProcessContent` names them, `mc:MustUnderstand` and compatibility errors refused), complex fields followed across paragraphs and table cells within their story (a story ending inside a field's code refused), hidden text, headers, footers, footnotes and comments left out, headings from the built-in `Heading 1`-`9` and `Title` styles with offsets into the stored text, one page per document. python-docx opens only a copy of the zip whose members were read within the sizes the validator bounded. The import check now also refuses zip members compressed other than stored or deflated and member names used twice. Not wired into the job queue yet.
- Sandbox runner (`vault.jobs.sandbox`, ADR 0005): runs an allowlisted `vault.` function on bytes in a child Python process with a timeout and a memory cap (`[processing] sandbox_timeout_seconds` and `sandbox_memory_mib`; a Job Object with kill-on-close on Windows; `RLIMIT_AS`, a parent-death signal and a seccomp filter that refuses to start another process on Linux, so the cap is the total there too), passes the input through a pipe, brings the result back as ASCII JSON (never a pickle) that the server builds into the type the entry point declares (checked when the entry point is defined: plain values, lists, tuples, optionals and plain dataclasses of these, without an `InitVar`, `__post_init__` or an `__init__` of their own) with an explicit converter, and only after its bytes show that decoding it costs the server at most 1 GiB and 4 million values, keeps the child's output off the console, and raises a fixed error class per outcome (timeout, memory, crash, the child's exception by class name only, unusable result, refused, unavailable). Nothing calls it yet.
- Search page in the app (`/search`): a keyword search over `POST /api/search` with the query kept in the page's state only (never in the address, the history, the browser's form memory or the console), one result per document with its name linking to it, its type, page (for a PDF), section path, match count and snippet, the matched words marked from the backend's segments as React text and never HTML, a filter by type, pagination up to the backend's largest offset, and fixed texts for no match, a query the grammar refuses (422, no retry) and every other error (with **Try again**); a 401 brings the token notice back.
- Chunk stage (`vault.ingest.chunk_stage`, job stage `chunk`, registered with the worker pool): chunks the current version's stored pages with `structural-1` and stores them with their keyword index rows, but only if the version still holds the bytes the job names; takes every decision that ends the attempt (stale, no pages, pages changed) under the write lock from what the database holds then, and chunks again (up to three rounds) when the version or its pages changed since its snapshot; makes the document `searchable` in the same transaction (a document in the trash stays there and comes back `searchable`); retries a version with no stored pages yet; logs nothing. Nothing queues `chunk` jobs yet. A job of any stage that uses up its attempts, in a worker or at start-up recovery, now makes its document `failed` in the same transaction, unless the job is no longer its document's current work for its stage (the same rule as Retry). A handler that stores its result marks its job done in the same transaction (`JobQueue.complete(..., connection=...)`, `Completion.RECORDED`), so a crash after the chunks are stored can no longer let start-up recovery fail a searchable document on its last attempt; a failed attempt the handler decides is recorded in that transaction too (`JobQueue.fail(..., connection=...)`).
- Pause and resume background processing: `GET /api/processing` gives whether the worker pool is paused and how many jobs each stage has in each status, `POST /api/processing/pause` and `/resume` change it and answer with the flag alone, so an error from either means nothing changed (the pause runs in a worker thread and answers once no claim is in progress, so no new job starts after it; a pause lasts until a resume or a restart); the Dashboard gets a Processing card with the counts and a Pause/Resume button, which asks only once the browser has access, asks again every 5 seconds while the tab is visible (never two requests at once, none during an action), and after a pause or resume loads the status again whatever the outcome, showing that it could not be loaded rather than an old status. A poll that answers after an action began is dropped. Nothing is logged beyond the pool's fixed events.
- Retry of failed processing: `POST /api/documents/{id}/retry` (`JobQueue.retry_document`) queues again, with all its attempts, each failed job that is its document's current work for its step (its input is the one the document needs now and no later job has that input; any other failed job stays as history), with a `retryable` flag on each job of `GET /api/documents/{id}` from the same rule, which the page uses to show the button, moves a `failed` document back to `processing`, wakes the workers and returns the document as it now is; a document in the trash is refused (409) and an unknown id is a 404. One transaction holding the write lock decides and writes, so pressing twice queues the work once. The document's page gets a **Retry failed steps** button above its processing table. Only a count is logged.
- Keyword search `POST /api/search` (`vault.retrieval.keyword`): the query in the body, read with a small grammar of its own (phrases in quotes, a trailing `*` for a prefix, every term must match, codes such as `CSE485` and `CSE 485` found either way) and turned into an FTS5 expression in which the owner's text is only ever quoted strings, so nothing typed is an operator or a syntax error; documents in the trash and older versions left out; one result per document with its best chunk by BM25, its page, offsets and section, the number of matching chunks and a snippet as text segments with matched words marked by a per-request random marker, and the name and section titles marked the same way, since they are searched too; stable paging, a filter by type, limits of 500 characters and 16 terms, fixed-text refusals and nothing logged. Nothing writes chunks yet.
- Text view of a document's extracted pages: `GET /api/documents/{id}/pages` returns the current version's pages with their headings a window at a time (at most 100 pages and about a million characters, the first page always whole), says `extracted: false` until the text has been extracted, and never logs page text; the document's page in the app gets a Text section that shows each page as plain text with its number, an outline of headings that jumps to them, and previous and next windows.
- Backup `.\vault.ps1 backup -To <folder>` (`python -m vault.backup`, `vault.storage.backup`): a `VACUUM INTO` snapshot of `vault.db`, consistent while the app runs, in a dated folder `snapshots/<UTC time>/` with the settings file and the token (owner-only, as ADR 0016 says), plus every original file the snapshot lists that the folder does not hold yet, each copied to a temporary name, checked against its hash and exact size (`BlobStore.put(expected_sha256=..., expected_size=...)`) and published read-only. Leaves out `index.db`, `derived/` and logs; never overwrites a snapshot; refuses a folder inside the vault, inside a Git repository or reached through a link or junction; tidies up after an interrupted run, re-sealing any original or snapshot file a killed run left writable; prints counts only. No retention yet.
- Chunks table and keyword index (`chunks`, `chunks_fts`, migration `0005`), chunker v1 (`vault.ingest.chunking.structural_v1`) and repository (`vault.db.chunks`): pages are cut at headings and packed into chunks of at most 600 approximate tokens (ending at a paragraph or sentence after 400 where possible) with a short overlap, each chunk traceable to its page and offsets; a version's chunks are replaced in one transaction after a check against the stored pages, and an FTS5 index (porter unicode61) over text, title and section path is kept in step by triggers. The permanent delete removes a document's chunks and their index rows in its transaction. Not written by anything yet.
- Permanent delete `DELETE /api/documents/{id}` and **Delete permanently** on a trashed document's page, behind a confirmation that it cannot be undone: only a document in the trash (409 otherwise), every row that belongs to it in one transaction under the write lock, then each blob no remaining version uses, decided again under the lock so an import or restore of the same bytes never loses a blob it needs; a crash between the two leaves the file to the start-up orphan sweep, and only counts are logged.
- Public reference texts for the OCR and PDF spikes in `demo/corpus/references/`, generated by `demo/generate/references.py` from the same content the renderer draws: one `NAME.txt` per screenshot and receipt (the drawn text in reading order) and a `NAME.txt` and `NAME.headings.txt` per text PDF, at each file's own path. They are not documents (the manifest does not list them and no eval question cites them), and tests check them against the drawn pictures and the PDFs' own bytes, so `ocr` and `pdf` can now be run on public data with `--references`.
- Text and Markdown extractor (`vault.ingest.extractors.text`): decodes by byte order mark, else UTF-8, else the Windows code page set in `[processing] text_fallback_encoding` (Windows-1252 by default), refuses a file that is not text as a whole by the validator's own rule, stores `\n` line breaks, and finds the top-level Markdown headings with markdown-it-py's CommonMark parser (ADR 0018; front matter skipped, headings in quotes and lists not recorded) with offsets into the stored text. Not wired into the job queue yet.
- Import page in the app (`/import`): drop several files or choose them, upload them one at a time with one import batch per drop and each file's modification time, and show each file's outcome (imported or already in the vault with a link to the document, refused with a fixed text for the reason, not sent after a refused token or a closed vault, or unknown after a 5xx or a lost connection), while the queue keeps running on other pages and never logs a file name.
- Integrity check `vault.ps1 check` (`python -m vault.check`, plan section 17): SQLite's integrity and foreign key checks on `vault.db` and `index.db`, every blob re-hashed, every entry in the blob store that is not a blob sorted by kind (link, hard link, one hash under several names, other), and the database compared with the store (versions whose blob is missing, blobs no row records or no version uses). Read-only, safe beside the running server, reports counts, kinds and content hashes only, and exits non-zero on any problem.
- sqlite-vec spike results (`docs/spikes/01-sqlite-vec.md`), measured on the owner's Windows PC on 2026-10-17: the extension loads, exact search matched a plain-Python search on 5 of 5 queries, and 1,024-dimension exact KNN took 28 ms per query at 10,000 vectors and 300 ms at 100,000, with a recommended conclusion (keep ADR 0004; exact search slows past roughly 100k chunks, sooner than the plan estimated) awaiting the owner's confirmation. The sqlite-vec spike now measures a WAL-mode database with `synchronous=NORMAL`, as the application uses, and stops if the folder cannot hold one; the recorded run used the rollback journal, so its insert rates are to be re-measured.
- **Move to trash** and **Restore** on a document's page in the app: one button for the document's current place, which shows the state the backend returns and a short confirmation, is disabled while its request runs, shows a fixed error text when the backend refuses (4xx), loads the document again and shows it as it is when the outcome is unknown (a 5xx, a lost connection or an answer that does not prove the move), and brings the token notice back on a 401.
- Worker pool (`vault.jobs.worker`, ADR 0005): threads in the server process that claim jobs per stage up to a configurable limit (`[workers]`), complete them or record the failed attempt by class name, sleep until woken instead of polling, pause and resume, and stop on shutdown. A claim still in progress when the pool is paused or stopped gives its job back unstarted (`JobQueue.release`, which also returns the attempt), and `pause()` waits for it. Started with the server after recovery; no stage has a handler yet.
- Start-up sweep for blobs that no database row uses (`vault.ingest.orphans`, `BlobStore.set_aside`): each is moved, unchanged and read-only, to `blobs/orphans/` instead of being deleted; links and doubled names are only counted, a failed move does not stop start-up, and only counts are logged.
- `make-manifest` for the spike scripts (`python -m vault_spikes make-manifest --corpus FOLDER`): lists a folder of the owner's own files and its subfolders into the `manifest.json` the embedding spike reads, with kind, size, SHA-256, PDF page count, `pdf_text` or `pdf_scan` by whether any page has text (pypdfium2), OCR need and exact duplicates (equal bytes that are also read the same way; the corpus loader refuses a duplicate mark between files read another way). Links, junctions, hidden files, unreadable files and other kinds are skipped and counted, only counts are printed, an existing manifest is kept unless `--force`, even one that appears during the run (published by an operation that refuses an existing name, also on FAT and exFAT), and the file is written atomically and read back with the spike's loader first. Spike reports are now created exclusively too, so a report that appears during a run is not replaced, and the cleanup of a failed write removes a name only while it still holds the file the run created.
- Pages table (`pages`, migration `0004`) and repository (`vault.db.pages`): the extracted text of each page of a document version with its headings, extractor version and encoding, replaced as a whole in one transaction and checked on the way in and out (contiguous page numbers, headings inside their page and in order, a canonical codec name). Not written by anything yet.
- Documents section in the app: a library page (`/documents`) with Library and Trash tabs, sorting by date added, name or size, paging, and the view kept in the address; a page for each document with its hash, version, imports and processing steps; and **Download original**, which fetches the file with the token and saves it under the document's name.
- Trash and restore: `POST /api/documents/{id}/trash` and `POST /api/documents/{id}/restore` move a document to the trash and back, keeping its state, file, versions, imports and jobs; both are idempotent and return the document as it now is.
- Download of a document's original `GET /api/documents/{id}/file`: the current bytes as an attachment, under the first import's name, with the validator's media type.
- Document details `GET /api/documents/{id}`: hash, current version, every import source and the processing jobs, read from one snapshot (`vault.db.engine.read_snapshot`).
- Document list `GET /api/documents`: one page of the documents in use or in the trash, sorted on the server by time added, name or size, with the name of the first import, the size and type of the current version, and the total.
- Upload endpoint `POST /api/imports/upload`: one file as the request body, its name, batch and modification time in headers (never in the address), streamed to a staging file under the size limit and handed to the importer.
- Project licence: Apache-2.0 (`LICENSE`, ADR 0017), declared in the backend, frontend and demo generator package metadata; the backend's wheel and sdist include the licence text.
- Import of one file (`vault.ingest.importer`): validate, store the blob, validate the stored copy, then record a new document with its version, source and `extract` job, or a new source for the document that already holds the same bytes. Concurrent imports of the same bytes make one document.
- Persistent job queue (`vault.jobs.queue`, `jobs` table, migration `0003`, ADR 0005): enqueue without duplicates, an atomic claim, back-off and a failed state after the last attempt, retry, and recovery at start-up of jobs a killed process left running. Error messages are never stored, only the exception's class name.
- Document tables (`blobs`, `documents`, `document_versions`, `import_sources`, migration `0002`) with ULID ids (`vault.db.ids`) and CHECK constraints on every value the application writes, a current version that must belong to its document, and the `trashed` state of ADR 0005 with the state to restore; the first part of Phase 1. Nothing writes them yet.
- Launcher `vault.ps1` (`install`, `run`, `stop`, `dev`) for Windows PowerShell 5.1 and PowerShell 7: it builds the app, starts the server in the background, waits for it, opens the browser with the token in the address fragment (ADR 0016) and stops it again, with PowerShell tests and a `Launcher (Windows)` CI job that runs the commands against a real server. It refuses a port that something else holds, makes commands started together take turns, keeps a vault folder with non-ASCII letters intact in its record, opens the browser only once the process it started answers with its own random launch id (`/api/health` and Vite's `/__vault/launch`), and never removes the record of a server it did not end (`docs/launcher.md`).
- Security headers on every response (`vault.core.headers`): a Content-Security-Policy that allows scripts only from this origin as files and sends requests, images and fonts nowhere else, plus `nosniff`, `no-referrer`, no framing and same-origin opener and resource policies, as ADR 0016 recommends before pages show document text. Checked in Chromium against the built app with no policy violations.
- Phase 0 spike scripts in `scripts/spikes/` (sqlite-vec, embedding model, OCR engine, PDF extraction) that record metrics only, with unit tests that use fakes and a CI job. Nothing has been measured yet; the spikes run on the Windows PC.
- Seven "find the document" questions in the public eval set (`find_document: true`, reworded from existing lookups in `demo/generate/questions.py`), so the embedding spike can report document-level Hit@1 on the public data.
- Access token in the page (`frontend/src/api/token.ts`, ADR 0016): the page takes the token from the address fragment `#token=...`, removes it from the address bar, keeps it in `sessionStorage` and sends it as a bearer header; without one it shows a notice with a password field and makes no request that would be refused. The API client, a session check on the dashboard and tests for each are included.
- Content-addressed blob store (`vault.storage.blobs`): hashing copy into `sha256/aa/bb/<hash>.<ext>`, read-only blobs, exact-duplicate handling that is safe under concurrent imports even under different extensions (a claim on the hash), an integrity error when a non-blob (a folder, a symbolic link or a junction) occupies a blob's place or one of its folders, a scan that reports every odd entry, start-up recovery (`clean_temp()` then `seal()`), `seal()` to restore read-only blobs after a crash, atomic publication with temporary-file cleanup, a size limit, `verify`, `scan` and `delete`.
